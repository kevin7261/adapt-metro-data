# 河流在骨架化與網格化中的處理（route-skeleton-river）

本文件是河流骨架化與網格化處理的**規格權威**（系統說明，**不是** skill）。
實作在 `src/stores/skeleton.js` 的 `buildConnectSkeleton` 與
`src/stores/schematicGrid.js` 的 `placeBlacks`。骨架化的整體規格見系統說明
`route-skeleton-connect`；網格化見系統說明 `route-skeleton-grid`。

> 節點一律用**類型名**（轉乘站／末端站／中途站／轉彎站／分隔站／交叉點…），
> 不以預設繪色當類型（見 `route-skeleton-connect` 對照表與 `src/lib/nodeTypes.js`）。
> Hover＝類型色點＋類型名（`popupHtml`；與地圖／D3／圖例同源）。

## 河流是什麼

河流由 `buildLandmarkCombined`（`scripts/buildLandmarkCombined.mjs`，Node 產線腳本）把河流地標轉
成**站級 route feature**：中心線**全點保留**＝每個折點都是 river 站、
`route_id` 格式 `river:…`。轉成 Point + LineString feature 後，河流對骨架而言
**就是一般的網路路線**——與地鐵完全一模一樣。

## 骨架化：除了分隔站準則，其餘零特例

除了分隔站準則（見下），`buildConnectSkeleton` 對河流**不做特例判斷**。河流 route 與
地鐵 route 一視同仁：

- **交叉點**（② `detectCrossings`）：河流與地鐵（或河流與河流）的線段
  交叉照通用邏輯產生合成節點。`featRoutesOf(f)` 直接讀
  `f.properties.routes`——河流已是一般 route feature，無需特例。
  **面域環線例外**（使用者裁決 2026-08-06：「公園不用計算交叉點（黃點），只有 river 才要算」）：
  `detectCrossings` 的 `routeArr` 會濾掉 `area:` 開頭的 route——地鐵從公園／皇居底下穿過
  不是拓撲交會，標成交叉點只會在環上多出一堆沒有意義的合成節點。河流照舊要算（過河＝橋）。
- **匯流轉乘站**：兩條河流在同一個站匯流 → degree ≥ 3 → 轉乘站。
- **末端站**：河流末端 degree ≤ 1 → 末端站。
- **中途站**：河流邊的中段直通站。

### 轉彎站：完全相同

河流邊與地鐵邊使用**同樣的轉彎站邏輯**（使用者裁決：不要特別不同）：

1. sinuosity 關卡：`PINK_SINUOSITY = 1.25`（弧長 ÷ 弦長 ≤ 1.25 → 不標轉彎站）。
2. 相對 Douglas–Peucker：`PINK_DP_TOL = 0.25`（perpDist ÷ 子段弦 > 0.25 才保留）。
3. 被保留的中間頂點必須是中途站。

### 分隔站：圖面長度比例（`GRAY_MAX_SPAN_RATIO` ＝ 10%；**只有地標線**）

2026-08-08 使用者裁決：「條件不是只能是他在這個圖面上的長度的比例嗎？比例太高就要切段，
比較準」。**只套地標線**——同日再裁決不動地鐵（`METRO_GRAY_EVERY = 5` 原樣保留），
理由見下方「為什麼不順便統一地鐵」。

演算法：兩個邊界點（節點／轉彎站／切斷站）之間的一段，若**弧長 ÷ 全圖對角線 > 10%**，
就把最接近該段弧長中點的中途站升成分隔站，再對切出來的兩半遞迴，直到每一段都低於門檻。
段中間若沒有可升格的中途站（相鄰兩站本身就隔很遠）就切不動，**這是真實上限、不是失敗**。

**順序鐵律：一定要在轉彎站標完之後才算分隔站**（使用者 2026-08-08：「地標的切斷點是要在
計算完轉彎站後才看要不要」）。分隔站量的是「扣掉轉彎站之後**剩下**的段還有多長」——轉彎站
與切斷站都是段邊界，所以轉彎站已經切開的地方不會再多放一個分隔站。實測（只算地標邊）：

| 城市 | 地標折點 | 轉彎站 | 分隔站 |
|---|---|---|---|
| 東京＋地標（皇居環） | 305 | 8 | **0** |
| 紐約＋地標（中央公園環） | 214 | 1 | **0** |
| 巴黎＋地標（塞納河） | 219 | 1 | 3 |
| 倫敦＋地標（泰晤士河） | 909 | 1 | 1 |

東京與紐約**一個分隔站都不需要**：轉彎站已經把環切得每段都短於門檻。把這段搬到轉彎站之前
的話，整條邊會被當成一段，兩城各會憑空多出好幾個沒必要的分隔站。

**為什麼不是「每 20 個中途站切 1 個」**（2026-08-06～08-07 的地標線舊規則）：
那個準則量的是**折點密度**，不是圖面長度，而要控制的是後者。實測「相鄰兩個有色點之間的
段長佔全圖對角線」（**下表地鐵那幾列是當時評估「要不要一起改」量的，最後裁決不改**）：

| 城市 | 舊規則最長段 | 新規則（10%）最長段 |
|---|---|---|
| 台北 | 27.2% | 15.4%（剩下的是**切不動**的長站距） |
| 東京 | 19.8% | 9.8% |
| 東京＋地標 | 19.8% | 9.8% |
| 紐約＋地標 | 14.0% | 10.0% |
| 上海 | 27.0% | 9.8% |
| 高雄 | 26.4% | 9.3% |

舊規則把切點花錯地方：地標線被切成 0.8～2.1% 的碎段（紐約＋地標 42 個分隔站）。
改成長度比例後切點數自然有界（每段最多 ⌈L/(τ·D)⌉−1 個，與折點密度無關）。

**為什麼不順便統一地鐵**：上表看得出地鐵也會變好（台北 27.2%→15.4%、上海 27.0%→9.8%），
但那會改變**全部 599 城**的骨架，而含地標線的城市只有 **13 個**（`-lm` 那批）。
使用者裁決「只改地標」——不做非必要的改動。要統一的話先算清楚全球重烘與基準重比的代價。

**這推翻了「切越多、跨距越長」的舊結論**。實測最長跨距（網格化後）：

| 城市 | 舊規則 分隔站／格網／最長跨距 | 新規則 分隔站／格網／最長跨距 |
|---|---|---|
| 東京＋地標 | 19／104×104／**57 格** | 30／115×115／**41 格** |
| 紐約＋地標 | 42／168×171／74 格 | 17／147×148／**64 格** |
| 東京 | 10／87×87／39 格 | 29／106×106／**35 格** |
| 紐約 | 32／159×159／67 格 | 17／144×143／**62 格** |
| 上海 | 26／160×160／50 格 | 25／159×159／48 格 |

紐約與上海是**每一項都變好**（分隔站更少、格網更小、跨距更短、段更短）。舊結論之所以
相反，是因為當時的切點花在密集折點上——格網被撐大了，長段卻沒被切到。

**仍然成立的是「不可由跨距回授決定」**（2026-08-06）：那指的是拿**網格化之後**的跨距
回頭決定切點，會自我放大（切越多 → 有色點越多 → 格網越大 → 跨距更長；當時實測
157×163 → 240×242、最長 18 → 39 格、單鏈跑不完）。現在量的是**投影前、網格化前**的
靜態幾何，不構成迴圈。

**門檻為什麼是 10%**：τ ∈ {6, 8, 10, 12}% 全掃過，10% 在兩個地標城市都給出最短的最長跨距
（東京＋地標 41 格、紐約＋地標 64 格），分隔站數又比 8% 少三分之一。6% 會讓格網明顯變大
（東京＋地標 154×154），12% 的跨距反而回升（46 格）。

**尺度不變**：門檻是「比例」不是像素，所以 bake（1200×800）與畫廊縮圖（200×200）必然
得到同一份骨架——這正是 `checkGridParity` 在守的假設。實作上要注意 raw lon/lat 不能直接
量：Mercator 把緯度方向拉長 1/cos(φ)，直接用 `dist()` 會低估東西向的段（東京
cos 35.7° ≈ 0.81，低估 19%），所以 `skeleton.js` 先做局部等角化（`figXY`）再量。

### 分隔站**不保證**最終段就短

切點只是「這裡可以轉折」，切完之後**九條直線化演算法會自由移動這些點**——
`SPAN_CAP`（見系統說明 `route-span-cap`）只擋 movewise 的移動，擋不到直線化本身。
所以加分隔站對「最終佈局的最長段」的效果**逐城不同**——舊規則時代實測過（②直角爬山的
最終佈局，地標段）：不放分隔站 vs 每 20 個切 1 個，東京＋地標 最長 18 → 12 格（變短），
紐約＋地標 16 → 35 格（反而變長，中央公園那圈被 ortho 拉開）。

**分隔站要解的是「一整段沒有轉折點」**（線畫起來像一條長直棍、跟地理形狀完全脫節），
不是「保證最終跨距 ≤ n」。上面那張「最長跨距」表量的是**網格化階段**（切點剛放好、
還沒被直線化搬動），那一層新規則確實普遍變好；但直線化之後的數字仍然逐城不同。
真要限制最終段長，得動直線化那一層（例如把段長放進①〜⑨的成本），那是另一件事。

## 網格化：零特例

`buildSchematicGrid`（`src/stores/schematicGrid.js`）對河流**也是零特例**：
河流的端點／匯流／轉折站與地鐵站一樣定義格線（`denseCuts`）、進 `cellOf`、
被爬山最佳化。

### placeBlacks 的地標線直線效果

`placeBlacks`（`schematicGrid.js` 的 export）把骨架邊的非中途切點之間的中途站
線性內插（等分直線）。地標線的切點＝轉彎站＋交叉點＋**分隔站（圖面長度超過 10% 就切）**，
所以線在切點之間仍是直的，但不會出現十幾格都沒有轉折的長直線。

## 渲染：河流色

河流在 D3 視圖上的線色 ＝ 路線的 `route_color`（`buildLandmarkCombined` 設定的
河流顏色）。`stationColor`（`src/lib/metroDraw.js`）不特判河流站——河流站的
`is_control`/`is_interchange`/`is_terminus` 照 `classifyStationRoles` 結果決定
節點類型（進而取預設繪色）。河流地標描邊色（`landmarkStroke`）＝`NODE_COLOR.cyan`（`#00E5FF`），
這是地標層自己的處理，不進骨架。

## 面域地標（皇居／公園）＝封閉環線，規則與河流相同

**使用者裁決 2026-08-06：「他們也是跟河流一樣要計算」。** 在這之前皇居／中央公園只是
地理底圖上的一片綠色 overlay，`skeleton.js` 明文略過 `Polygon`——所以「只有面域、沒有河流」
的東京＋地標與紐約＋地標，從 2 GRIDDING 起每一張圖都跟 base 城市一模一樣。

現在 `scripts/_landmarkAreas.mjs` 的 `areasToRoutes()` 把面域**外環**（`coordinates[0]`；
內環／湖心島不轉）**全點保留**轉成**封閉環線 route**：

- 每個折點是 `area: true` 的車站 Point（`station_id` 前綴 `nar`）；
- 路段 `route_id = area:{landmark_id}`、色 `#22c55e`（`NODE_COLOR.green`）；
- `stations` 陣列尾端重複第一站、幾何尾端重複第一點 ＝ 閉環（同 Moscow Circle line 的寫法），
  骨架自然把它判成 `cls=loop` 的邊。

**骨架與網格化對它零特例，只剩一處分流**：**不參與交叉偵測**——`detectCrossings` 濾掉
`area:` route（使用者 2026-08-06：「公園不用計算交叉點（黃點），只有 river 才要算」；
河流不在此列，過河＝橋，照舊要算）。所以面域環線上只會有轉彎站、切斷站與分隔站，
沒有黃色交叉點。

（第一處分流＝分隔站準則：地標線用圖面長度比例、地鐵用每 5 個。2026-08-08 之前兩者
都是「每 N 個」、只差常數 20 vs 5。）

**填色面**：`Polygon` feature 仍留在合併檔裡當**地理視圖的原圖**；示意圖（骨架／網格化／
直線化／Frame）的那片綠色由**環線節點的現在位置**現算（`src/lib/landmarkAreas.js` 的
`areaFillPaths`），所以面會跟著佈局變形——照 Polygon 的地理座標畫會得到一片停在原地、
跟路網對不上的面。D3 主視圖（`buildDrawData.areaData` → `drawScene` 的 `area-layer`）與
所有縮圖（`viewGeometry` 的 `areas[]`）同源，滿足「視圖≡顯示」鐵律。

## 實作契約

- 地標線（河流／面域環線）在 `buildConnectSkeleton` 裡與地鐵的差別只有**兩處**：
  ①⑥ 的分隔站準則（`isLandmarkEdge ? splitRun : everyRun`）；②`detectCrossings` 排除面域環線。
  分類、轉彎站、收縮全走同一段程式。
- 分隔站的門檻＝`GRAY_MAX_SPAN_RATIO`（`skeleton.js` 匯出，現行 `0.10`）。度量用 `figXY`
  局部等角化後的弧長，分母＝全網對角線；`opts.grayMaxSpanRatio` 可覆寫，**只給實測掃描用，
  不是 UI 設定**（工具列的「河流分隔曲折度」早已整組移除，不要再加回可調參數）。
- `skeleton.js` 另有 `SKELETON_FP_SALT`（指紋鹽，凍結字面值）；`grayInfo` 從未實作，
  分隔站的 hover 說明由 `popupHtml.grayWhyText` 依門檻現算。
- **hover**：分隔站的類型行下面會多一句「為什麼在這裡」，三種擇一——地標線＝
  `style.leg.nodeGrayWhySpan`（比例）、地鐵＝`style.leg.nodeGrayWhyMetro`（每 N 個）、
  `bend:` 合成折點＝`style.leg.nodeGrayWhyBend`（交叉修復，見 `route-skeleton-grid`）。
  判地標一律用 `isLandmarkNode(p)`（`river || area`），不要只問 `river`。
