# 網格地圖直線化的評價方式（route-grid-straighten-eval）

本文件是該評價方式的**規格權威**（系統說明，**不是** skill）。實作必須與它相符。

## 評什麼

**①〜⑨ 各鏈的程式網絡循環結果**（`3-straightening/grid/algorithm-<鏈>/network-loop/`），
也就是九條直線演算法鏈跑完 movewise 四步鏈之後的收斂佈局。

- **不評 post**（鏈自己的結果）——那是循環之前的中間狀態，不是拿來畫版面的東西。
- **不評 LLM 鏈**：LLM 直線化／LLM 網絡循環是「契約固定、方法不固定」的求解者，
  結果為快照級可重現，依 CLAUDE.md 的不變式**不可與①〜⑨並列做效能比較**。
  它們照樣畫在九宮格裡，只是不進評價表、也不會拿到「最佳」tag。
- 九個候選吃的是**同一份輸入**（同城市的網格地圖）與**同一套硬規則**，所以可比。

## 七個指標與優先順序（2026-08-08 使用者裁決）

使用者給的是**優先順序**，不是等權：「水平垂直／45度線／銳角少／總線段少／長度少／網格少」，
並確認「總線段少」與「長度少」**是同一件事**（就是總長度）→ 合併成一項；方正度保留、排最後。
同日再裁決加入**「同路線越直越好」**，並指定**插在「45 度線段」後面**（＝第 3 位）。

| # | 指標 | 定義 | 方向 | 權重 |
|---|---|---|---|---|
| 1 | 水平垂直線長 | 所有 H/V 段的長度總和，單位＝格（**計分用占比** `hvLen/totalLen`） | **越長越好** | 7/28 |
| 2 | 45 度線段 | `|dx| == |dy|` 且皆非 0 的段**條數**（計分用 `diag/segs`） | **越多越好** | 6/28 |
| 3 | 同路線彎折 | 彎折成本合計：同 route 的每一對段，直穿 0／一般轉角 1／銳角 2（計分用 `bend/segs`） | **越少越好** | 5/28 |
| 4 | 同路線銳角 | 同一個頂點上、屬於**同一條 route** 的兩段夾角 < 90° 的次數（計分用 `acute/segs`） | **越少越好** | 4/28 |
| 5 | 總線段長 | 所有段的歐氏長度總和（含斜段），單位＝格 | **越短越好** | 3/28 |
| 6 | 網格面積 | `cols × rows`（循環結果檔自己記的宣告網格） | **越少越好** | 2/28 |
| 7 | 方正度 | `min(cols, rows) / max(cols, rows)`，1＝正方 | **越大越好** | 1/28 |

**權重的數字是我選的、順序是使用者給的**：名次 1..7 給 7:6:5:4:3:2:1 再除以 28，只是「遞減」的
一種寫法。使用者沒有指定數值，要改就改 `rankStraightenEval` 的 `WEIGHTS` 並同步本文件。

表格欄位也照這個順序排（演算法 → 水平垂直線長 → 45 度線段 → 同路線彎折 → 同路線銳角 →
總線段長 → 網格面積 → 方正度 → 綜合分）。

### ③ 同路線彎折 vs ④ 同路線銳角：為什麼兩項都留

③ 是 ④ 的**嚴格上位**——每一對銳角同時貢獻 ③ 的 2 分，但 ③ 連一般轉角都計 1 分。
兩項都保留的理由是它們的鑑別力出現在不同的城市：

- **台北**：九條鏈的銳角**全部是 0**，④ 整批同值→中性 0.5、完全分不出高下；
  ③ 的值域是 **24–29**，照樣排得出名次。
- **新加坡＋LRT**：兩項都有值但**不同調**——④力導向銳角 65／彎折 234，
  ②直角爬山銳角 64／彎折 227，後者兩項都更好；而 `algorithm-path` 銳角同為 65
  但彎折 236，只看銳角會誤判成平手。

**③ 的定義與 `movewise.js` 的 `bendCostAt` 逐字相同**（含「直角不判得比鈍角貴」那條——
判貴會鼓勵 90°→135°，而 135° 必定伴隨一條 45° 段，反而壓低排第一的 H/V 占比）。
這樣評價量的正是收斂後拉直 pass 在最佳化的那個量，兩邊要改一起改。

**曾經考慮但不是使用者的意思**：「總線段少」也可以解成**可見線段條數**（同 route 共線的相鄰段
合併後的條數，台北實測 38–44，與長度不重疊——②直角爬山線段最少 38 卻總長最長 101.4）。
使用者確認**不是**這個意思，所以沒有實作。

**彎折與銳角都只算同一條 route**（`sharesRoute`）：不同路線在轉乘站交會成什麼角度，不是
「這條線被折得很難看」。判準用**內積與外積**、不用反三角函數：外積 0 且內積 < 0 ⇒ 共線直穿；
內積 > 0 ⇒ 銳角；其餘 ⇒ 一般轉角。

段的分類（`segClass`）：`dx==0 || dy==0` ⇒ H/V；`|dx|==|dy|` ⇒ 45°；其餘 ⇒ 其他（不計分）。

**為什麼一個算長度、一個算條數**：使用者原話就是「水平垂直線越長越好、45 度線越多越好」，
照字面實作。兩者量綱不同不影響——排名前會各自正規化。

**長度一律在整數格座標下算，不可以用畫面 px**：每個視圖的 `cellPx` 由自己的 `cols`／`rows`
決定，px 長度跨視圖根本不可比；而且 `cellPx` 非正方時角度會被拉歪，45° 判斷會直接判錯。

全系統可調參數的總表（在哪、現值、改了要連帶做什麼）＝系統報告 `TUNABLE_PARAMS_REPORT_2026-08-08.md`；
本文件是本節參數的**規格權威**。

## 怎麼算分

七項在**這九個候選之內**各自 min–max 正規化到 `[0,1]`（彎折、銳角、總長、面積是越小越好，
取 `1 − norm`），再依上表**權重加權平均**成綜合分；**最高分者全部**掛「最佳」tag。

- 整批同值的項目給**中性 0.5**（給 1 會把所有分數一起墊高；兩種做法對**排名**都沒有影響，
  0.5 只是讀起來誠實一點——沒有鑑別度的項目本來就不該替誰加分）。
- **同分要用容差比，不可以用 `===`**：分數是七個浮點數的加權平均，數學上完全同分的兩條鏈
  （台北的⑥八向格網與⑨彈性格網每一項原始值都一樣）在位元上不保證相等。判準＝
  `|score − top| ≤ 1e-9 × max(1, |top|)`。
- 這是**組內相對分**，不是絕對品質分；跨城市的分數沒有可比性。

### 台北實例：第 3 項存在的理由

九條鏈吃同一份骨架、段數都是 74，所以條數本來就可比。台北的關鍵觀察是——
**銳角整欄都是 0**（④ 整批同值 → 全給中性 0.5，完全分不出高下），
**彎折卻是 24–29**，實際在分名次。新加坡＋LRT 則是兩項都有值但**不同調**：
④力導向銳角 65／彎折 234，②直角爬山銳角 64／彎折 227（兩項都更好），
而 ⑦路徑簡化 銳角同為 65 但彎折 236——只看銳角會誤判成平手。

**這裡刻意不放完整的分數表**：`network-loop` 一重跑，每一格數字都會變，
貼上去的表隔天就是錯的（違反「所有文件一定跟程式內容對齊」）。要看當下的數字，
打開「評價」分頁即可——那才是權威。

## 顯示

**版位＝底部面板的一個分頁**（2026-08-07 使用者裁決：先做右側，再改到 bottom view
「用表格方式顯示，比較容易 sorting」，最後定案「要跟其他 bottom view 一樣、也可以拖拉」）。

- 位置：3 直線化「網格地圖」圖層 →「視圖顯示」→ 底部面板的 **「評價」分頁**。
- **它就是 `AttributeTable` 的一個 tab**，不是另做的面板。曾經另寫一個
  `StraightenEvalPanel`，就算複製了類名仍是第二份實作，樣式與行為都對不齊
  （少了關閉鈕、表格用成資訊面板的 `prop-table`）。現在共用同一個元件 →
  同一列 `.panel-tabs`、同一張 `.table-scroll` 表、同一套欄位排序與欄寬拖拉、
  同一顆關閉鈕、同一個高度（`store.attributeTableHeight`，與物件列表共用）。
- **並排總覽只留「評價」一個分頁**（`evalOnly`）：物件列表／JSON／Skill 需要「單一圖層」，
  九宮格沒有那個圖層，掛上去沒有意義（使用者指出）。`panelTab` 在 `evalOnly` 時
  恆夾成 `'eval'`——舊 session 若存著 `'list'`，分頁會全被 `v-if` 藏掉、面板變空白。
- **入口在工具列**：視圖顯示不掛「圖層操作」那組（`LayerChromeActions`），所以底部面板
  本來完全打不開。StyleBar 在 `mosaic && evalView` 時多一顆「評價」開關，語意與
  `LayerChromeActions.toggleTable` 相同（關→開到該分頁；已在該分頁→關閉）。
- **每一欄都可以排序**：表頭寫法與物件列表同一套（`th` 帶 `tabindex`／`role="columnheader"`／
  `aria-sort`，`@click` 與 `@keydown.enter/.space`，箭頭用 `MIcon.th-sort`），
  所以鍵盤也能排序。第一次點是「好→壞」（面積／銳角／總長升冪，其餘降冪），再點反轉。
- **「?」說明每一項怎麼算**（2026-08-08 使用者要求）：工具列右側一顆 `btn-icon`＋`help` 圖示，
  開 **`HelpModal`**（＝視圖列 LayerDoc／方位算法同一個殼，**不可自創彈窗**；`/design` 的
  Dialog 區有登記）。內容是八段 `.help-sec`（七個指標＋綜合分），每段 `h3` 帶一個
  `MIcon` ＋ `.help-prose` 內文，逐項寫「原始值怎麼算／計分用什麼／為什麼這樣設計」。
  - 段落由元件的 `EVAL_HELP` 表驅動（icon／標題 key／內文 key），**順序與 `EVAL_COLS` 一致**；
    加指標時兩張表都要加，否則說明會跟欄位對不起來。
  - i18n key＝`d3.evalHowTitle` ＋ `d3.evalHow<指標>`；內文含 `<b>`／`<br>`／`<code>`，
    所以用 `v-html`（與 `style.orient*Body` 同一個做法）。
  - **icon 只能用 `src/lib/uiIcons.js` 已登記的**——本段用到
    `straightening`／`polyline`／`route`／`diagonal_line`／`line_weight`／`grid_on`／`rectangle`／`functions`。
    第一版寫了 `change_history`／`grid_4x4`，兩個都沒登記（要嘛先登記、要嘛換掉，這裡選換掉）。
- **最佳列**用表格既有的 `.selected` 列樣式；徽章與畫廊卡的贏家章共用 `.vc-badge`
  （2026-08-07 由 `CityViewGrid` 的 scoped style 提升為全域，兩處才不會各長一個樣）。
- **名次：1–9 全部都寫**（2026-08-08 使用者裁決「最佳 tag 改成寫名次，1-9 都要寫」；
  在此之前只有贏家那格掛一個「最佳」）。
  - **位置＝卡片標題的子標行**（`.city-head-row2`），同日第二次裁決「名次 tag 改寫在上面
    標題的子標」——原本疊在縮圖上（試過右上、再改左上），會擋住圖；而且**一張卡＝一條鏈**，
    卡內兩格是同一條鏈的兩個階段，名次本來就屬於整條鏈，掛在單一格上是錯的層級。
    所以名次是**掛在 `card` 上**（`card.evalRank`／`card.evalBest`），不是掛在 tile 上。
  - 它是**行內 tag**，與 `.vc-badges`（`position: absolute` 那組縮圖角標）無關；
    `.city-head-row2` 是 `display:flex; align-items:baseline`，直接放進去即可。
  - **第 1 名沿用贏家黃**（`.vc-badge--all`），第 2 名以後用中性底（`.vc-badge--rank`）——
    全部上黃色，黃色就不再有「這條最好」的意思了。
  - 文案＝`d3.evalRank`（`第 {n} 名`／`#{n}`），`title` 用 `d3.evalRankTitle` 寫全句。
  - **底部「評價」分頁的那一顆同步改成名次**（同一組類名、同一份 `rank`），
    表格與卡片不會各說各話。
- **4 版面地圖也要寫名次**（同一次裁決）：`buildFrameGridMosaicView` 現在也跑一次
  `rankStraightenEval`，**用的是同一組 ①〜⑨ 循環佈局**，所以兩處名次必然一致。
  Frame 欄只是把同一份佈局重新畫線、不改座標，因此該鏈的輸入格與 Frame 格同屬一張卡、
  共用一個名次。LLM 直線化不進評價（評的是①〜⑨），沒有名次就不顯示。
- 表格與徽章**同源**：分數由 `buildGridAlgoMosaicView` 算一次傳給兩邊，面板不自己再算，
  否則兩處可能給出不同答案。

## 不落檔

評價是**現算**的（打開分頁就算），不寫任何結果檔、不進資料流圖、也沒有圖層列。
理由與 movewise 的移點／移線／移枝／併格相同：它不是管線的一步，沒有下游吃它的輸出。
換城市、重算、改鏈都會重新算一次，所以永遠與畫面上的九張圖一致。
