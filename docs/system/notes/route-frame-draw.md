# Frame Maps 版面路網畫線（route-frame-draw）

本文件是該演算法／規格的**規格權威**（系統說明，**不是** skill）。實作必須與它相符。

> **前端殼層的窄屏／RWD 使用體驗**（側邊抽屜、工具列收合）在 [[ui-responsive]]——
> 與本檔「示意圖隨版面變形」的演算法無關。

把 system note `route-hillclimb` 的**縮減網格**（`d3.stepCompact`）佈局重繪成示意圖折線：方向數可以是
**任意／4／8／16**（見下方「線的方向數」）。本文件是這些畫線規則的**唯一權威**。

> **硬規則：八方向約束以「版面 pixel」為準**——H/V/45° 是在 SVG 螢幕座標裡判定，
> **不是在整數格索引裡**。預設的畫法**隨版面變形**（欄寬 ≠ 列高是正常的）；工具列的**版面**
> 下拉（`style.layoutTitle`＝「模擬 Frame 的版面尺寸」；`style.frameAuto`＝「目前版面」）可以切成固定
> 尺寸（`src/lib/frameBoards.js` 的 web／phone／IG 預設群組，類似
> Illustrator 的工作區域）——該寬高就成為畫線的座標系，SVG `viewBox` 置中留邊，用來模擬 Frame。
> 格座標上的對角線在螢幕上不是 45°，所以折線是在**目前畫布的 pixel 空間**裡重建；只要視窗／版面
> 尺寸一變，就在新的 pixel 座標**重跑 buildFrameMap**（同尺寸的重繪走快取）。曾試過「固定正方
> 虛擬格網＋等比留邊」把佈局凍結（與裝置預設無關），**使用者裁決不要**——隨版面變形才是正確
> 行為；裝置預設是後來加上的模擬開關。（副作用：格子不是正方時，A* 只能走 H/V 步——對角步在
> pixel 上不是 45°；只有格網剛好是正方時才自動啟用 8 方向。）實作：
> `src/stores/frameMap.js` 的 `buildFrameMap(segs, pos, opts)`；UI 在 `D3Tab.vue`（`layer.type === 'frame'`），
> 圖層群組「Frame Maps」；版面預設在 `src/lib/frameBoards.js`。
>
> **`buildFrameMap` 的 7 個子模組（`src/stores/frame/`，2026-08-02 D2b 抽出；一行程式碼都沒改）**：
> `frameMap.js` **直接 import 5 支**——`frame/geometry.js`（方向族判定、腿的重疊／交叉判準、`Z`／`TOL`／`OVER_TOL` 常數）、
> `frame/scoring.js`（`makeScoring`：`conflictCount`／`orderViolation`／`pickBest`／`nearOverlapLen` 等評分與硬規則）、
> `frame/lattice.js`（`makeLattice`：A\* 格點救援 `routeLattice`）、`frame/resolve.js`（`makeResolve`：
> `routeAll`／rip-up／成對重算／擠壓與共線救援）、`frame/passes.js`（`makePasses`：收尾 pass 群——
> 減折／L→45／去階梯／去 22.5／角度平衡）。
> 另 2 支由子模組 import——`frame/candidates.js`（候選折線族，`resolve.js` 與 `passes.js` 用）、
> `frame/heap.js`（最小二元堆，`lattice.js` 用）。共 **7 個模組檔**。
> `frameMap.js` 本身只剩初始化、用 `ctx` 把四個 factory（scoring→lattice→resolve→passes）串起來，
> 以及收尾（`placeWhiteStops` 把中途站放回）。**factory 的呼叫順序＝原本的執行順序，不得對調**（見該處註解）。
> ⚠ 動到其中任何一個模組都要跑 `node scripts/checkFrameParity.mjs`——它會把真實的城市 × 來源 ×
> 鏈 × 階段 × 方向數餵進 `buildFrameMap`，把輸出與基準快照**逐 bit 比對**。

## 資料流

```
Hill Climbing 圖層的縮減網格（compactGrid cells）
  →（矩形圖層＋有矩形時）循環可以移動方形的頂點，但不可破方；
    LLM 對齊／評價會把矩形座標釘回去
  → 轉成像素座標（等寬的格中心）
  →（`mergeParallelSegs` **已停用**——Frame 不得改動 3 直線化交下來的段集合，見下）
  → buildFrameMap：每一段挑一條 H/V/45 折線；**矩形的邊（兩端都是凍結的 members
    ＝灰白 highlight）強制 S→T，絕對不可折彎**
  → 黑點沿選定折線的弧長平均放回
```

矩形圖層（`orig-shape-rect`；旋轉移除後已無 `rot-shape-rect`）有矩形時，灰白高亮的矩形邊在 Frame 裡
**絕對不可變動**（`opts.frozenIds` ＋ `shapeLock`；不要求 pixel 上的 H/V；成對 rip 只能讓另一條線
繞路，不得破壞矩形邊；見 system note `route-shape-rect-align`）。

> **不變式：每一個非中途站（切點端點）都必須落在格網交點上。** 它們是整數格佈局的格心，Frame 只
> 在它們之間畫折線，不得移動非中途站（只有中途站會沿弧長放回）。曾試過把 degree-2 同線
> 轉彎站折進內部以拉直階梯（`mergeThroughSegs`），那會把非中途站移離格網交點——
> **使用者裁決不要，已移除**。要減少階梯只能靠佈局端（hillclimb／縮減網格）讓那些節點更共線；
> Frame 這端不能移點。

### 合併共軌路線（`mergeParallelSegs`）——⚠ **2026-08-10 已停用**

> **鐵律：Frame 完全不可以改 3 直線化的結果**（2026-08-10 使用者裁決，同日並說「不要亂合併路線」）。
> Frame 這一階**只准重畫折線**，段的集合、拓撲、哪些邊存在，一律照直線化交下來的原樣。
>
> 本函式違反這條：它把「同一對端點的兩條邊」併成一條，並把其中一條**刪掉**。
>
> **實際症狀（大阪，使用者回報）**：天王寺 ↔ 交叉點 `x0` 之間有兩條邊——
> ① 直達（`rm8028805`）、② 經阿倍野（`rm8028879`）。骨架把它們標成 `parallel`（頭尾共點），
> 並插了**切斷站阿倍野**——那個點存在的唯一目的就是「這兩條必須分開畫」
> （見 CLAUDE.md「切斷站＝缺幾個補幾個」：`parallel` 需 1 個，否則兩條邊會完全重疊）。
> 機制 (A) 卻把直達邊併進繞路邊：直達邊的路徑只有兩個端點，覆蓋守門**必然放行**。
> 結果是那條直的對角線消失、顏色被交錯畫到 L 形折線上——畫面上看起來就是兩條線疊在一起。
> **3 直線化沒有這一步**（只有 Frame 呼叫它），所以同一張圖走到 Frame 就變了樣。
>
> 現在 `mergeParallelSegs` 是 **identity**（原樣回傳）。實測 10 城的 ①筆畫法：
> 1310 段裡原本會被吃掉 8 段（0.6%），6 城受影響。
> 停用前的實作保留為 `mergeParallelSegsLegacy`（**無呼叫端**）——要恢復「重疊就一條」，
> 得先解決它與切斷站的矛盾，不要直接接回去。
>
> 以下保留停用前的規格，供回溯與日後重新設計參考。

**（已停用）合併共軌路線**（原裁決：Frame 必須看起來像匯入的網絡——重疊就是一條
線，不是幾條互相偏移的平行線）。判定一律看**匯入的真實幾何**，與官方路網圖的語意無關。兩個
機制：

- **(A) 端點相同**：兩條以上的骨架邊共用**同樣的兩個切點端點**（快車加慢車，或任何共用端點的
  路線）→ 站數最多的那條成為代表，其餘的 routes／routeColors 併進來、seg 丟棄。
- **(B) 幾何重疊（快車跳過中間的轉乘節點）**：快車邊 E 的**整條 `edge.geom`** 落在另一組邊的軌
  跡上（`maxDev < TAU≈10m`，`TAU = 1e-4`），即使它跳過中間的樞紐、端點也對不上——因為快車實際上就跑在同一條
  軌道上（共軌路線在資料裡共用同一組座標，偏差 ≈0），而網絡本來就畫在那條軌道上。找出所有落在
  E 軌跡上的邊；若它們連起 E 的兩端、且總站數 > E 的站數（E 是比較稀疏的快車側），就把 E 併進
  那條鏈的每一段、丟棄 E 的 seg。TAU 非常緊（~10m），所以相距數十公尺的**平行但不同**的軌道不
  會被誤併。

**覆蓋守門（關鍵，絕不可略過）**：只有在被併掉那條邊的**每一站**都已經在保留的路徑上時才准合
併——否則被丟棄的 seg 上的**獨有車站**會**變成孤立點**（畫面上有點沒有線，嚴重錯誤）。幾何重疊
**不等於**同一條線：獨立的線（例如 Sydney Metro）可以與市郊鐵路**共軌**卻有自己的車站，這種情
形**絕不合併，維持各自獨立**。可安全合併的例子＝兩站直達快車（兩站都是走廊上的共用節點，沒有
獨有車站）。機制 (A) 與 (B) 都套用這道守門。全量 **599** 城：**0 個孤立車站**。

若代表邊的 cls 因此帶了 ≥2 種顏色 → coline（由 strokesOf 交錯畫）。環線
（`e.a===e.b`）不參與。純函式，依序判定（router 對 seg 順序敏感），在繞線之前套用。副作用：線
變少 → 衝突變少。全量 599 城：0 次 fallback、0 個例外、0 個孤立車站。

**停用後的連帶影響**：底襯顏色會變。`drawFrame` 用的是 `L.seg.edge.cls`，合併時
`parallel`（頭尾共點・藍）會被改寫成 `coline`（共線合併・紅）；不合併之後那些邊維持
`parallel`，Frame 的底襯顏色就與 3 直線化一致了（大阪天王寺那兩條邊即為此例）。

**環線邊雙向去重（在 `buildFrameMap` 內、繞線之前）**：`buildStraighteningGraph` 會把環線（包含單線
自交，例如拿坡里 1 號線的 Vomero 髮夾彎——`skeleton.js` 在自交處補的交叉點把那條線切成
`cls==='loop'` 的環）輸出成**雙向**——每條環線邊都出現兩次、端點對調。兩份畫在同一條軌跡上，
router 為了避開重疊會把它們平行偏移成**糾纏的雙輪廓**。所以在繞線之前，凡 `cls==='loop'` 且無序
端點對 `{a,b}` 已經出現過的 seg 就丟棄，每條環線邊只畫一次：雙生邊是冗餘幾何（同樣的
routes／顏色），丟掉不損失任何東西，而環線改以單一乾淨的環呈現。實測閉合性不變（去重後環線城
市的所有環節點仍是偶數度＝閉合）：格拉斯哥 4、古爾岡 8→4、新加坡 28→24、拿坡里（自交造成的假
環）6→3（一個乾淨的直角三角形）。真正的環線（單向繞行、每條邊的端點對唯一）不受影響。

- **視圖畫廊**（LayerPanel 工具列的格狀按鈕 → `openAllGalleryTab`／`GALLERY_TABS`，

## 候選折線（依折點數遞增）

方向判定（pixel 座標，容差 `TOL=0.75px`）：`Δy≈0`→H、`Δx≈0`→V、`|Δx|≈|Δy|`→45°（D±），
`|Δy|≈T22·|Δx|`→22.5°（E±），`|Δx|≈T22·|Δy|`→67.5°（F±），其餘都不合法（X）。
`T22 = tan(π/8) ≈ 0.4142`。

**線的方向數（`opts.dirs` ∈ {0, 4, 8, 16}，工具列四選一，預設 8）**：可以用到哪一級的方向。
**方向等級的優先序是 tie-break，不是硬性關卡（使用者最終裁決）**：0/90 能畫就不要用 45，45 能畫
就不要用 22.5°/67.5°，離散族能畫就不要用任意角——但這個優先序**只在衝突數相等時**適用；
「明明有一個不重疊的 22.5 畫法卻沒用」是錯的。衝突數（含貼行重疊）排在方向等級之前：零衝突的
22.5° 勝過會重疊的 45°。
- **任意方向**（`dirs === 0`，`style.dirAny`＝「任意方向」）——任何 S→T 直線都合法（**直線優
  先**，規則 0 的走廊包含任意角）；非 H/V 的角度不限於 45/22.5。要繞路時仍可展開完整的 16 方向
  候選族，另外還會產生「同角度平行偏移」（被擋住時先沿邊挪開，角度不變）。衝突／貼行把任意角腳
  段視為族 `G`（`ang` ＋一個法向鍵）；只有角度差 ≤≈3.4°（`ANG_PARALLEL=0.06`）才算同族——
  **只有在無可避免地非常接近時 → 斜邊取同一個角度**。收尾的 `angleBalancePass`：節點上的出射角
  盡量平均分散；太靠近的可動折線會被對齊成與鄰邊相同的角度。直線絕不為了平均分散而多一個折點。
  `pickBest` 的方向等級：H/V → 45 → 22.5 → 任意角。
- **4 方向**（只有 H/V）：完全不產生 45° 候選；45° 直線視為不合法（改用 L）；`legalDetours` 的
  H/V 平行偏移變成**純正交**（V–H–V／H–V–H，不是 45° 三角形）；正方格網上 A* 的 8 方向與 45° 巨
  觀斜出**都關掉**（純正交繞線）；**pass 2 的 L→45（`l45Pass`）跳過**。實測：每個城市 45° 都
  ＝0。**決策程序與 8/16 方向完全相同（使用者規定：三個方向等級共用同一套程序）**：對角段用
  **同一組骨架**（L、雙折 50/25/75、四折／多折階梯），差別只在每個 45° 腳段會展開成 H/V（兩種順
  序都試，同方向的腳段合併，再依折點數重新排序）；A* 救援照常使用（純正交步進）。
  **注意**：展開 45° 腳段（整條線共用一個 vhFirst）產生不了「真正的 Z」——V–H–V 的中段必須是
  H、兩端都是 V，而展開只會產生多一個折點的階梯。所以 4 方向**另外直接產生真正的 Z**：
  `V–(tΔy)–H–V` 與 `H–(tΔx)–V–H`，t ∈ {50%, 25%, 75%}（`pushCand`，zRank 順序 50→25→75）。沒有這
  一族就會出現「本來可以在 25% 轉彎、卻畫成壓在另一條線上的階梯」這種錯誤。切點順序是
  **50% → 25% → 75%**：衝突數與重疊長度都相等時 50% 一定勝出；為了**不要重疊太多**，25%/75% 的重
  疊比較短時可以贏過 50%（見下方「候選挑選順序」④→⑤）；畫完仍然重疊的段，收尾的
  `overlapReducePass` 會在同折點數下改用其他切點再試一次（見下文）。端點、連通性與局部走向都不變
  （拓撲保持）。8/16 方向不產生正交階梯（對角改用 45° 候選）。收尾的接續軟調整（softPass）與減折
  重掃在 4 方向下照常執行。
- **8 方向**（＋45°）：現狀（H/V/45°）。
- **16 方向**（＋22.5°/67.5°）：加入 22.5° 族（E±＝22.5°，F±＝67.5°）。幾何族：
  `dirOf`／`lineKey`（E±：y∓T22·x，F±：x∓T22·y，`T22=tan22.5°`）／`spanOf`（F± 用 y）／`perpGap`
  （E/F 除以 `NORM_EF=√(1+T22²)≈1.082`）全都支援；`legsCross` 是一般化的線段相交，天生就支援。
  **22.5° 候選（`skew:true`）在 `pickBest` 裡平等競爭**（以前這是硬性關卡，「只有 45 完全不合法時
  才放行」——使用者裁決改掉：明明有不重疊的 22.5 畫法就必須用）：先比衝突數，再比近距離貼行，
  第三才比 skew → 零衝突的 22.5° 勝過會重疊**或近距離貼行**的 45°；兩者都乾淨時仍是 45° 勝出，所
  以 22.5° 絕不會無故被畫出來。
  **候選族（2026-07-20 擴充）**：除了單折的（斜＋軸向，共 4 種）之外，還有
  **雙折 22.5 族**（斜–軸–斜／軸–斜–軸，切點 50/25/75）與**混合 45＋22.5 族**
  （45–軸–斜／斜–軸–45，使用者規定：**同一條線可以混用 45 與 22.5**）——所有斜腳段之間仍以軸向
  腳段隔開（斜接斜仍然禁止），且全部標 `skew:true`（衝突數相等時仍是 45 這一級勝出）；每個腳段都
  必須長於 `2×TOL`（次 pixel 的腳段會被 dirOf 誤判）。沒有這些族，「45 到處衝突、單折 22.5 也衝突，
  但混合 45＋22.5 就不會重疊」的段就會被逼成貼行／長繞路／forced。
  **「45 能畫就不要用 22.5」的兩項加強（2026-07-20，台北藍線案例）**：
  - **成對重算也要遵守方向等級**：`jointReroutePairs` 的候選改依 `(skew, bends)` 排序，聯合目標是
    字典序的（skew 腳段數、總折點數）——以前只比總折點數，導致單折 22.5 會贏過乾淨的雙折 45。
  - **22.5 → 45 升級（`deskewPass`，每一輪收尾都跑，放在 destairPass 之後）**：22.5 是「現在 45 到
    處衝突」的暫時解，等衝突解決後走廊往往已經空出來，但減折與軟調整都不會為了換方向等級而多加
    折點，所以 22.5 一旦畫下去就永遠留著。收尾的重試：對含 22.5/67.5 腳段的線，只要存在
    **乾淨的 45 等級候選**（零衝突、近距離貼行與硬重疊都不得變長、環繞序不變），就換成折點最少的
    那個——**折點數允許增加**（方向等級排在折點數之上）。貼行守門沿用先前的裁決：若 45 的形狀必
    須貼著另一條線跑，就保留不貼行的 22.5。`rerouteAround` 的乾淨候選同樣依「近距離貼行 → skew」
    挑選；`overlapReducePass` 可以往上換到 22.5 等級，但要求硬重疊或近距離貼行嚴格變短（硬重疊不
    得變長）。雙折 45° 的切點優先序固定為 **50% → 25% → 75%**。
    **減折（`bendReductionToFixpoint`）與軟調整（`softPass`）仍然不得把 45 等級「減折」成 22.5 等
    級**（那兩個 pass 不是拿來消除重疊的）。UI：工具列的**方向數群組按鈕**（`StyleBar` 的 Frame
    那一列；`style.dirsTitle`＝「允許的線方向數」），共**四**個按鈕——`style.dirAny`（任意方向）／
    `style.dir4`（4方向）／`style.dir8`（8方向）／`style.dir16`（16方向）——→ D3Tab `frameDirs` →
    `buildFrameMap` opts.dirs
    （會摺進 Frame 快取鍵）。

1. **直線** `S→T`：本身就已經是 H/V/45 → 0 折。
2. **單折**：45° 先跑到與較短邊相符處，再接 H/V；純 L 形（先 H 後 V／先 V 後 H）；鏡像（先 H/V、
   以 45° 收尾）。
3. **雙折**（兩個鏡像族，折點數相同，各有 1/2·1/4·3/4 三個版本）：
   - **(a) 45–H–45 / 45–V–45**（斜–平–斜，**兩端都是 45°**）：中段坐落在 1/2，衝突時移到 1/4、
     3/4。
   - **(b) H–45–H / V–45–V**（平–斜–平，**兩端軸向、45° 在中間**，使用者規定：`hv-45-hv` 也必須存
     在）：45° 覆蓋對角線的 m，兩端的軸向段平分剩下的 |Δx−Δy|。當兩端直接續進鄰段時，這比 (a) 讀
     起來更順（讀作一條線）。pass 2 依接續角度在 (a) 與 (b) 之間挑選。
3½. **三折混合（使用者的案例 `vh-45-vh-45`）**：`軸–45–軸–45` 與 `45–軸–45–軸`（軸＝較長軸的 H 或
    V）。雙折族的軸向腳段只能坐在**起始列與結束列**；這一族把中間的軸向腳段抬到**中間的列／欄**
    ——45 的升段切點 rf 與軸向腳段切點 hf 各取 {50%, 25%, 75%}（3×3×2＝18 個候選）。當起始與結束
    兩條走廊都被別的線占住時，這是唯一的三折解；沒有這一族，該段就被逼成貼行（琥珀）或跳到四折
    階梯。
4. **一般化交替階梯（使用者規定：`vh-45-vh-45` 或 `45-vh-45` 可以**無限制**重複，只要畫得正確，折
   點最少的合法候選就勝出；唯一的硬規則是「45° 一定接 H/V」＝45° 絕不相鄰）**：45° 腳段與軸向腳
   段（較長軸的 H 或 V）**交替任意次數**，且四種頭尾組合全部產生——`45…45`（多一個斜）、
   `軸…軸`（多一個軸）、`45…軸` 與 `軸…45`（數量相等，兩種順序）。均勻切點（≤4 折的族另外帶
   50/25/75 切點變體）；有腳段短於一格（u）的組合會被跳過＝段數自然被幾何限制住（另有 ≤20 折的硬
   上限防止候選爆炸）。折點數不需要事先偏好——`pickBest` 的「衝突最少 → 折點最少」會自然收斂到最
   短的合法交替。兩個較舊的固定族仍在：
   - **同軸**：45–H–45–H–…–45（ax>ay）或 45–V–45–V–…–45（ay>ax）。每個升段＝m/k，餘量全部沿較大
     的軸切成 k−1 段。只有 45° 與一個軸向方向，讀起來比較乾淨 → **優先嘗試**（k=2 時另有 1/2·1/4·
     3/4 的踏階位置變體）。
   - **混合（k=3）**：45–H–45–V–45 與 45–V–45–H–45。每條對角取 <m/3（3g<ax 且 3g<ay），讓 H 與 V
     各留一段餘量 → 用在必須同時沿兩個軸避障的時候。更複雜的排列交給 A* router 處理（它同樣遵守
     45°→H/V 的規則）。**45° 的腳一定被軸向直線隔開，不會形成被禁止的 45°→45° 轉角**。被採用時
     計入 `stats.multi`（多折；純回傳值，工具列不顯示）。折點數的絕對優先序不變——只有在段數更少
     的候選全部衝突時才會選多段候選。
5. **Fallback**：只有上述全部衝突時才畫原方向的直線（不是 H/V/45），計入 `stats.fallback`。

**重疊優先於折點數（使用者規定）**：能直就直——唯一的權威敘述是下方的**規則 0**（此處不重述）。
非直線的段，**重疊線數最少優先於折點數最少**——L 少一個折點，但如果它的共線長度比較長，就改用
50／25／75 的 Z（或多一階階梯）。順序見下方「候選挑選順序」。衝突解決之後另有一次**減折重掃**
（`stats.straightened`）：變成真正的直線仍然優先；其他的減折不得讓軟共線變長。它包含
**協商拉直**——當比較直的畫法只被 1–2 條線擋住時，就把那些線 rip 掉、採用直的畫法、再讓被擋的線
重新繞線，全部乾淨才提交。唯一的例外是「共用兩個端點的雙生線」，它們不可能都直（會完全重疊），
所以一定有一條要繞路。
> **為了「能直就一定要直」這條鐵律，折點預算被放寬（`bendReductionToFixpoint`）**：協商拉直平常
> 要求**總折點數嚴格下降**才提交；但當這條線因此**變直**（`c.bends===0`）且
> **沒有犧牲掉任何原本已經是直線的線**（`ripsStraight` 檢查 `saves[k+1].bends===0`）時，就**沒有
> 折點預算**——本來就已經彎的鄰居必須讓路，不管要多加幾個折點，都要讓這條線變直。
> 收斂保證：直線數嚴格遞增，且直線絕不會被弄彎。
> **但仍然是全部乾淨（沒有新的交叉／重疊）才提交**——去交叉的重掃／rip-up 仍可能 rip 掉任何線
> （包含直線），因為殘留交叉（forced）比彎掉的線更糟。

**禁止 45° 接 45°（使用者規定）**：折線不得有兩個相鄰腳段都是斜的（不同族亦然）——因此 H/V 線
**沒有合法的單折繞路**（唯一的單折選項是 45-45 三角形，而它被禁止），只剩雙折平行偏移；A* 同樣
禁止斜接斜的步進與巨觀接合。

**禁止正交階梯，對角走向用 45°（使用者規定，最高目標之一）**：折線不得有**連續的直角折點**
（`H-V-H` 或 `V-H-V`＝一階一階的階梯，`vh-vh-vh`）——對角走向的段必須用 **45° 斜線**畫，不是正交
階梯。合法：45° 斜線、`45-H-45`、`vh-45-vh`（直角之間被 45° 隔開；單一個 L 也可以）、多階 45° 階
梯（`45-H-45-H-45`）。不合法：兩個以上**同型的直角折點接在一起**（中間沒有 45° 或直線）。45° 與
軸向部分的切分不限於 1/2，也可以是 1/4、3/4（見雙折候選的 `[0.5, 0.25, 0.75]`）。
> **A\* 階梯 → 45°（`destairPass`，2026-07-20 實作）**：非正方版面上 A\* router 只能走 H/V 步（對
> 角步在 pixel 上不是 45°，見上方硬規則），所以救回來的路徑是正交階梯。收尾迭代的**第一步**是一
> 個後處理：在每一條 A\* 畫出來的線上（routed，跳過 squeezed/colinear/forced），抽出「連續交替 H/V
> 且有 ≥2 個直角折點」的階梯子段，在該子段的兩個端點之間用**同一組 8/16 方向候選**
> （含 pixel 空間的 45° 腳段，排除 skew 等級）重畫再接回去——折點數不得增加，必須含斜腳段或折點
> 嚴格更少，整條線必須無衝突，貼行不得變長，環繞序不得改變，接合處不得斜接斜；全部乾淨才換進去
> （計入 `stats.diag45`）。殘留的階梯＝密集路網裡沒有候選塞得進去的角落。

**L→45（使用者最終裁決，`stats.diag45`）**：純「水平＋垂直」的直角折線，若把其中一邊改成 45° 不
會與任何線重疊，就改成 45° ＋軸向；**優先挑「該節點上同一條 route 的鄰段也是同方向的 45°」那
邊**——穿過節點仍朝同方向延續的斜線會讀作一條線。

**合法直線也需要備案**（共用兩個端點的平行邊，或走廊已被較早的折線占住），同樣依折點數排序：先
試**單折大繞路**（H/V 線用 45° 三角形頂點，45° 線用 L 轉角——不論位移多大，仍優先於兩折），再試
**雙折平行偏移**（45° 出去、以 d=1→2 格單位平行跑、45° 回來）。

## 絕不交叉的多層解法（依序升級）

「路線交叉絕對不允許」是最高優先的硬規則；當所有候選折線都衝突時，依這個順序升級：

1. **降衝突重掃**：全部繞完線之後，重新檢視每一條仍有衝突的線（交叉的雙方都重試），用完整資訊重
   選衝突數最少的候選，最多 4 輪。**個別重掃把另一條線當成固定的**（`placedOf(li)` 只排除自
   己）——雙方互卡、誰都繞不過去的情形，這樣解不了。
1b. **成對重算兩條線（`jointReroutePairs`，使用者規定：畫出來的線若會交錯，兩條線都必須重算；
    **出現交叉時必須確認這兩條線有沒有不交叉的畫法**）**：對仍然**彼此交錯**的一對（不同族的腳段
    `legsCross`，不是共線貼行），**一次 rip 掉兩條**，其餘所有線固定不動，聯合搜尋兩條線有界折點
    候選的**組合**（各取前 `JOINT_CAP=16` 個，全部依折點排序），取「兩條都乾淨（對其餘的線**以及彼此**）且
    **總折點數最少**」的那一組（折點數的絕對優先序不變）。它跑在**個別重掃的 A\*/rip-up 升級之
    前**（乾淨的組合勝過用 A\* 把一條線扭來扭去），重掃之後再跑一次，迭代到不動點（最多 3 輪）。
    動畫影格（`opts.fast`）會跳過。只有它解不掉的才繼續往下。
   - **入口＝直接偵測真正的交叉（`crossingPairs`，2026-07-20）**：先 bbox 預篩，再 `legsCross`，
     **與 forced 旗標完全解耦**——以前要求「兩邊都 forced」才進得來，因此漏掉最常見的交叉對「先畫
     時是乾淨的，後來被 forced 的線壓過去」（先畫那條的旗標從來沒被填上）。
   - **成對 rip 升級（`jointRipPair`，重掃之後的深度輪）**：有界折點的組合都塞不下時，rip 掉另一
     條線 → 自己用 A\* 畫 → 讓另一條線 `rerouteAround` 回來（兩種順序都試），**全部乾淨才提交**
     ——這是「這一對線到底有沒有不交叉畫法」的實質驗證。交叉是最高等級的錯誤：另一條線
     **即使是被鎖定的直線也會被解鎖讓路**（殘留交叉比彎掉的線更糟；直線只被動繞路、絕不自己跑
     A*，而且只有事後仍是乾淨直線才保住鎖）。**例外：矩形邊（`shapeLock`）絕對不可改**——不可當
     主動繞路的 F、也不可被拆的 W；只准對方繞過固定的矩形邊。全量 599 城實測：交叉對 139→112、
     forced 208→132、折點數只 +0.1%。
2. **A\* 格網 router**（`routeLattice`）：在半格格網上找一條**只穿過自由空間**的路徑（由構造保證不
   交叉、不貼行、不壓過點）。正方格網上對角步是合法的 45° → 8 方向；**非正方版面只能走 H/V 步**
   （對角步在 pixel 上不是 45°）＝會產生正交階梯——收尾的 `destairPass`（見上方「A\* 階梯 →
   45°」）再把階梯子段轉回 45° 折線。端點被同一條線的腳段完全占滿時，用 **45° 巨觀進出**（斜出＋
   一個直角折）接上格網；**有向淹沒預檢**（T→S best-first）會先跑——被封死在小口袋裡會立刻放棄，
   並回報「牆」是哪些線。折點數可以超過 2（算成多折／繞路）。**禁止大繞行（使用者規定
   2026-07：只在最短路線附近搜尋可能性，絕對不可繞整整一圈）**：A\*、淹沒預檢與巨觀進出都被限制
   在 **S–T 走廊視窗**內（端點 bbox 外擴 `LOCAL_PAD = 3×unit`），且總路徑成本（長度＋折點懲罰
   `TURN = 2×unit`）必須 ≤ `maxCost = 3×Manhattan + 8×unit`。走廊內找不到＝視為無路——淹沒撞到的走廊牆線會回報給
   rip-up，讓它拆掉一面牆在局部重畫（A* 因成本上限放棄時也會回報），再不行就走共線救援／forced。
   寧可在局部留一個琥珀色殘留衝突，也不要畫出一條繞了整張圖的線。A* 啟發函數使用加權 Manhattan
   （`W=1.4`，近貪心）；節點搜尋上限 `pops < 400000`。
3. **Rip-up & reroute**（PCB 繞線技術）：被封死時（Jordan——端點被其他線圍成的面關在裡面，數學上不
   存在不交叉的路徑），rip 掉被撞最多次的那條牆線（一條線 → 一對兩條，ranked 取前 4），先畫被困住的段，再讓牆線
   重新繞線；全部乾淨才提交。
4. **優先重啟**（協商）：仍然失敗的段在下一次**全圖重排序**時最先繞線（在牆築起來之前），原本的牆
   線改繞著它們走；最多 6 輪。
5. **擠壓救援**：仍然沒有路徑的段，用 60% 的貼行距離（`minGap * 0.6`）再跑一次 A*（交叉仍然絕對禁止）。
6. **共線救援（使用者規定：真的沒有更好的解時，最後手段允許共線；但絕對不允許新的交叉）**：連擠壓
   救援都救不回來的段，再放寬**「共線／平行貼行」約束**試一次——先跑有界折點候選
   （`conflictCount(..., crossOnly=true)`，依折點數），再跑 A*（`routeLattice(..., allowColinear=true)`，
   `blockerOf` 放寬 `legsHug`）。畫得出來就是**與另一條線共線但不交叉**（勝過殘留交叉）。
   **`legsCross`（交叉）與 `pointOnLeg`（壓過點）仍然絕對禁止**——只放寬平行貼行，絕不穿越。計入
   `stats.colinear`。共線是可接受的次佳解，優先於 forced。

只有上述全部失敗才會留下 `stats.forced`（殘留衝突）。數量本身不顯示，但每一條這樣的線**都會**在畫
布上標出來：`buildDrawData.js` 畫一層琥珀色 `EDGE_FORCED` 墊底加上 hover 說明——這些是**深層 Jordan
封閉**，連共線都無解（唯一的出路必須穿過圍住它的牆線＝交叉，rip-up 也解不掉）。全量 599 城實測：共
線救援救回 **23** 條線（否則就是 forced），剩下的 forced 是連 rip-up 都解不掉的極限（紐約／東京 JR／
巴黎等密集路網）。`stats.fallback`（不合法角度的 fallback）＝0。

## 衝突判定（否決候選，「路線之間不得重疊」）

1. **共線重疊／平行貼行**：同族（H/V/D+/D−/E±/F±；任意方向族 G 依 `angDiff≤ANG_PARALLEL` 判同族）的兩個腳段，**法向間距 < minGap（預設 0.35× 格單
   位）**且投影範圍重疊超過 `OVER_TOL=0.5px` → 衝突（幾乎同高／同寬的貼行也一併擋掉）。**總量上限（硬規
   則）**：一個段與已畫網絡的累積重疊不得超過該段畫出弧長的 **25%**；超過就淘汰該候選（不是「多一
   個衝突」）。共線救援也不得越過這個上限。
2. **線段相交**：不同族的兩個腳段只要有接觸就算衝突，**唯一的例外是端點對端點**（在共用節點相
   會，由 `isNodePt` 確認在格網節點上）。幾何交叉在骨架階段就已經變成交叉點；節點以外的相交不允許。**同一對線最多只能交叉一次
   （使用者規定）**：候選與**同一條**已畫線之間的第二個交點（交點座標會去重，橫跨對方轉角不重複
   計算）→ 直接淘汰（`Infinity`），不是「多一個衝突」；寬鬆 fallback 裡每多一個交點 +50。8/16 方向
   下即使交叉真的無可避免，也只准交叉一次。
3. **壓過節點**：腳段的內部（不含端點）掃過任何其他彩色節點（`pointOnLeg`）→
   **直接淘汰**（`Infinity`）；那會把沒有相連的點與線畫成相連，是拓撲錯誤，不可經由 forced／共線救援接受。寬鬆 fallback 裡 +100。
4. **折點不可以撞到別人的東西（使用者規定）**：候選折線的**內部折點**（轉折處，
   `pts[1..n-2]`）如果落在
   **(a)** 另一個彩色節點上，或 **(b)** 另一條**沒有共用端點**的線的折點上
   → **直接淘汰**（`Infinity`）；寬鬆 fallback 裡 (a) +100、(b) +50。
   兩者畫出來都是「看起來在這裡交會，其實兩條線根本沒關係」。
   **為什麼要另外寫一條**：上面第 3 條的 `pointOnLeg` 只認「嚴格落在腳段內部」，
   端點接觸是**刻意排除**的（那是正常的交會），而折點正好就是腳段的端點——
   所以第 3 條一個都抓不到。「沒有共用端點」是必要的限定：共用車站的兩條邊
   本來就該在那裡碰頭。實測（5 城 × 5 鏈的循環結果）折點壓站 5 → 1
   （剩下那 1 個走寬鬆 fallback，同第 3 條的處置），`forced` 大致持平。

5. **節點上的環繞序不得改變（rotation system，使用者鐵律）**：每個節點上相連各線的 **360° 環繞
   序**必須與輸入（縮減網格）中弦方向的參考順序相符（`segsAtNodeRef`）。H/V/45° 吸附可以改變「出射角」，但同一節點
   上不得有兩條線因此互換位置（順序改變＝拓撲改變）。實作為 `orderViolation(seg, pts)`：節點上已畫
   ≥3 條線時，「實際出射角」依參考弦角排序後的序列必須循環遞增（繞一圈最多一次下降）；相同的出射
   角（貼行雙生）算平手。每一個被採用的點都通過這道檢查——`pickBest`（寬鬆 fallback 改記 +200）、
   A* 結果、rip-up／rerouteAround、成對重算（帶著對方的暫定 rect override）、共線救援、擠壓救援與四
   個收尾 pass。
6. 段的處理順序：**矩形邊（shapeLock）最先** → **長走廊（乾淨直線）優先**（它們的替代路徑最少），平手時照原序，結果具確定性。

**硬違規的最後 fallback（寬鬆重掃）**：若每一個候選都超過 25% 共線上限或壓過外部節點，該段不會被
隱藏（看不見的線會讓中途站浮在空中，那更糟）；改成再重掃一次、放寬計分（`lenient=true`）——壓過車站 +100、超上限重疊
+50、環繞序違規 +200——畫出「最不壞」的候選並標 `forced`（琥珀色殘留衝突）。絕不會裝作合法悄悄畫出去。

**候選挑選順序（`pickBest`，pass 1 與衝突重掃共用；規則 0 的直線除外）**：
①**衝突最少** → ②**近距離貼行最短**（`nearOverlapLen`，間距 < **0.45** 格的平行併跑——使用者裁決：視覺
上的貼行也是「重疊」，而且排在 **45/22.5 取捨之前**；「右邊那個重疊本來可以用 22.5 解掉卻沒解」＝
一個貼著另一條線跑的 45 不得勝過完全不貼行的 22.5。門檻取 `unit * 0.45`：嚴格介於硬貼行 0.35u 與
合法半格間距 0.5u 之間——只抓「比合法半格更近」的併走；曾取 0.55u 把半格也算進去，結果台北
16 方向把正常 45 當貼線、降成 22.5）→ ③**方向等級**（H/V 優於 45 優於 22.5°，即 `dirTier`；任意角腿 `free` 最低）→ ④**折點最少**
（越直越好；規則 0 的直線在這之前就鎖定了，根本到不了這裡）→ ⑤**硬共線重疊最短**（4 方向下為了不
重疊，25%/75% 可以在這一階贏過 50%）→ ⑥**切點 50% → 25% → 75%**（`zRank`） → ⑦軟共線最短（一格以內近乎平
行）→ ⑧任意角折線罰分（`free && bends>0` 略遜於離散族同折數）→ ⑨**總路徑長度最短**（使用者規定 2026-07-20：線要盡量短——放在**最弱的一階**：只有其他所有準
則都平手時才挑比較短的繞路）。重疊全部相等時，50% 是預設的折點位置。`rerouteAround` 的乾淨
候選同樣先比近距離貼行再比 skew；`l45Pass` 改成 45 時不得新增近距離貼行。**共線救援**（forced 段的
最後手段）會在所有「只共線、不交叉」的候選中挑**重疊最短**的那個。

**畫完仍然重疊 → 移動切點（`overlapReducePass`，收尾的第一步）**：任何畫完之後仍有硬共線重疊的段
（含 forced 的），會在它**同折點數或更少折**的兄弟候選中重試（50%↔25%↔75% 切點、VH↔HV 順序）——衝突數不得
增加、交叉不得增加、硬共線必須嚴格變短才換進去。三個方向等級用同一套程序；實務上主要影響 4 方向（使用者規定：4 方
向的畫法若重疊，就試著移到 25%/75% 減少重疊）。

**規則 0：直線鐵律（使用者規定）——「能直就直」的唯一權威**：在目前的方向等級下，端點可以用
H／V／45° 直接相連、**且對已畫網絡零衝突**的段，一律畫成直線並鎖定。有重疊／交叉的「看起來像直
線」不得鎖定——它必須用 50%／25%／75% 或其他候選繞過去；超過 25% 共線或壓過車站就淘汰。
22.5°／67.5° 永遠不是可鎖定的走廊。兩條直線互撞時：先畫且乾淨的那條保住直線，後者改彎；絕不會讓兩
者都被鎖進一個重疊。

## 軟目標（衝突解決後的微調）

**同名路線要盡量少彎（使用者規定）**：同一條 route 穿過節點時應盡量續直。它排在重疊／折點數的挑選
之後（絕不為此增加共線或折點），落實在三個地方：

1. **接續軟調整**（`softPass`）：在**折點數相同**的無衝突候選之間互換（腳段族可以改變——L 形 ↔ 斜＋直都可以），
   以共用車站上同一條 route 的折線的接續角度計分（`contScore`），**轉角越大越好（使用者規定：180 優先，其次
   135、再來 90、最後 45）**——續直（180°）+1、135° +0.707、直角 0、銳角 45° −0.707，計入
   `stats.swapped`。不從 45 級換到 22.5 級。
   **跑兩次**（2026-08-09 使用者：「彩色點前後的路線要盡量要 直線／鈍角／垂直／銳角」）：
   收尾迭代裡一次，整條收尾鏈的**最後**再一次。理由是**時機**——鏈中間那次跑完，
   `bendReductionToFixpoint`／`l45Pass`／`angleBalancePass` 只看折點數與方向級、不看轉角，
   會把剛擺好的形狀換掉；補跑一次讓「同折點數的候選之間」由轉角品質定案。
   最後那次帶 **`keepDiag`**，見下面第 3 點的衝突裁決。
2. **單折候選的 45° 端放哪邊**：初始順序是固定的（45° 靠 a 端優先），軟調整再用接續分數覆蓋
   它——45° 放在哪一端能與同一條 route 的鄰段續成同方向的斜線就放哪端。
3. **L→45 能做就做（使用者規定）**：水平接垂直（單折 L）只要改成「45° ＋直線」不會與
   任何線重疊就**必須**改；兩個變體之間，優先選有「同一條 route 同方向 45° 鄰段」的那一端，再看整
   體接續分數。它放在**收尾迭代的最後**。

   ⚠ **它與「站上轉角越大越好」結構上互斥，取捨經使用者裁決**（2026-08-09）：
   `l45Pass` 讓那條腿以 45° 進站，站上的轉角就從 180° 變成 135°——兩條規定必然互相抵銷。
   實測「完全不准減少 45°」的收尾 softPass 與基準**一字不差**（`stats.swapped` 完全沒增加），
   也就是不動 45°，轉角那條要求就毫無效果。

   **裁決＝只有換到一個真正的直穿（180°）才准拿 45° 去換**（`softPass({ keepDiag: true })`
   的 `straightCount` 閘；為了 135°／90° 一律不准）。實測那樣保住的 45° 只比「轉角全面優先」
   多 5 個、效益相同——代表損失的 45° 幾乎都確實買到了直穿。
   所以 l45Pass 的結果**現在會被最後那次 softPass 修改**，但只在「換到直穿」這一種情況下。

   實測（台北／紐約／東京／巴黎 × 九鏈，dirs=8）——**折點 1831、forced 83、硬共線 1、
   fallback 0、交叉 0 逐項完全相同**，只有：
   直穿 2710 → **2877**（+167）｜銳角 104 → 101｜垂直持平｜45° 腳段 1790 → 1623。

收尾迭代：〔**A\* 階梯轉 45（destairPass，第一）** → **22.5 升回 45（deskewPass）** → 縮短共線（overlapReducePass） →
接續軟調整（softPass） → 減折到不動點（bendReductionToFixpoint） → **L→45（l45Pass）**〕跑**兩輪**（`phase < 2`），每一步移動走廊之後都重新挑選。
任意方向另外在每輪最後跑 `angleBalancePass`（節點角均分＋近角同斜）。
**兩輪跑完之後，再跑一次 `softPass({ keepDiag: true })`**（2026-08-09）——整條鏈真正的最後一步，
讓站上的轉角品質在「同折點數」這一層定案；`keepDiag` 保住 45°，只有換到直穿才放行。

## 黑點

黑點不是折線頂點：k 個點中的第 j 個放在所選折線**弧長**的 j/(k+1) 處（沿 a→b 的段方向，`placeWhiteStops`）。共用的黑
點（環線／折返路線讓同一站出現在兩個段上）由後處理的那一個決定。

- `buildFrameMap(segs, pos, opts)`：`segs` 來自 system note `route-hillclimb` 的
  `buildStraighteningGraph(skeleton, cellOf).segs`（含 `interior` 黑點 id 與母邊參照），`pos` 是
  **pixel 座標** `Map<id,[x,y]>`（縮減網格的格心），`opts.unit` 是繞路偏移單位（pixel，呼叫端傳大約
  一格），`opts.minGap` 是平行貼行門檻（預設 `unit * 0.35`）。`unit` 在內部一律取絕對值當保險——面板收
  合／拖曳期間的暫態尺寸可能算出**負的格寬**，而負的 minGap 會讓 legsHug 恆為 false、完全停掉貼行保
  護（畫出互相重疊卻沒被標成衝突的線）；host 尺寸 < 80px 時 D3Tab 也會直接跳過繪製（等
  ResizeObserver 量到真實尺寸）。開發診斷：`window.__frameAudit = true` 時，`stats._audit` 會列出畫完
  之後仍有殘留衝突、或被標成 forced 的線（用來找「有衝突卻沒被標記」的漏洞）；`window.__frameDebug`
  是最新的 `cachedFrame`（由 D3Tab 在 dev 模式掛上）。
- `FRAME_ROUTER_REV`（`'2026-07-25-free-dirs-v1'`）：摺進 D3Tab 的 in-memory Frame 快取鍵。
  routing 語義改變時 bump，使 Vite HMR 不會沿用舊 router 的折線。
- 回傳
  `{ lines: [{seg, pts, bends, fallback, forced, routed, lockedStraight, shapeLock, colinear, squeezed, legs}], posAfter: Map<id,[x,y]>, stats:
  {straight, single, double, multi, rerouted, fallback, forced, colinear, swapped, squeezed, straightened, diag45,
  restarts, segs}, hidden, hiddenMaxT }`。個別 `stats` 欄位的意義見上方各節；`hidden`／`hiddenMaxT`
  來自白站自動隱藏，見 system note `route-frame-weight`（`hiddenMaxT` 是全域截斷值 T，沒有隱藏任何東西時為
  null）。
- 純函式，無亂數；同樣的輸入給同樣的輸出。
- 繪製沿用 D3Tab 的路線配色（單線實線、共線交錯虛線）與節點分類顏色。

## 權重驅動的版面簡化

**權重**分頁（`style.weight`）——連結權重 → 非均勻欄寬與列高 → 在新的 pixel 座標重跑
buildFrameMap——加上動畫過渡、rAF 迴圈的自我調速、以及白站的自動隱藏，全部在
system note `route-frame-weight`。

## LLM 互動（`style.interactive`，StylePanel 分頁——**不是**視圖葉節點）

「權重＝尺寸」比例的第二個來源（第一個是 system note `route-frame-weight` 的流量權重）：使用者說一句話（例如
「把市中心那幾欄拉開」），LLM 推理**每個 X 欄／Y 列區間**的顯示權重——不改拓撲、不動格座標，只改顯
示上的欄寬與列高。細節（執行流程、權重規則、觸發端點）以 [[route-llm-grid]] 為權威；此處只記與本
文件共用的末端變形。

- 結果檔是 `maps/…/4-frame-maps/{source}/llm-grid/{chain}/`——**`{chain}` 是自己獨立的一層資料夾**
  （`networkFramePath(..., { chain })`；論文①〜⑨ 在磁碟上是 `algorithm-<chain>`，見 `chainLayerDir`）。
  裡面放 colW/rowW/model/note/userPrompt ＋指紋；路徑由
  `metroLlmGridResultPath`／`networkFramePath` 產生，不是舊的扁平名
  `data/metro/frame-llm-grid/`。離線由 `scripts/llmGrid.mjs` 的 export/apply 產生，網頁只負責載入
  （GH Pages 上一樣）；dev 時執行按鈕（`llm.startExec`）會 POST `/llm-grid/run` 去 spawn 一個
  headless Claude Code（`vite/llmTriggers.js` 的 `llmGridTrigger`，在 `vite.config.js` 接起來，與
  `/llm-straighten-align` 共用 `claudeSkillTrigger`）。
- **末端變形與流量權重是完全同一套機制**——區間權重 → `intervalAxes` → 新的 pixel 座標 → 重跑
  buildFrameMap → 動畫過渡（內插格線、fast 幀，同 §8.3，最後一幀完整品質）。
- UI：它是 StylePanel 的 **`grid` 分頁**（`style.interactive`＝「LLM 互動」；一個一句話輸入框＋一個
  執行按鈕＋一份結果記錄）加上畫布覆蓋層（執行中的串流輸出／尚未產生時的輸入框）。
  **`D3Tab.vue` 裡沒有 `mode === 'frame-llm'`**——繪製仍留在一般的 `frame` 模式，權重只改 pixel 軸。
  指紋仍然寫進檔案；資訊分頁顯示 `common.fpOk`（「與目前資料相符」）／`common.fpStale`（「可能過
  期——資料已更新」）（2026-07-30：有檔就開，不再依指紋拒載）。

## 修改這個轉換時

候選／衝突／黑點規則有變時，**本文件與 `src/stores/frameMap.js`（及 `frame/` 子模組）要一起改**；上游契約
（buildStraighteningGraph/compactGrid）有變時，同步 system note `route-hillclimb`。權重驅動的非均勻版面在
system note `route-frame-weight`。動到 `buildFrameMap` 行為一律要跑 `node scripts/checkFrameParity.mjs`。
