# 移點（route-endpoint-move）

本文件是該演算法／規格的**規格權威**（系統說明，**不是** skill）。實作必須與它相符。

movewise 四步鏈的**第 1 步**（移點 → system note `route-line-compact` →
system note `route-branch-shift` → system note `route-grid-merge`）。
輸入＝該鏈的結果佈局（論文①〜⑨＋LLM 直線化，見 system note `route-paper-align`）。
實作：`src/stores/movewise.js` 的
`buildEndpointStraightening(skeleton, cells, cols, rows, {limit, skip, anchor})`（單一掃描 pass；
函式名保留了歷史名稱）。`anchor` ＝位移上限的錨點，由循環傳入；沒傳就不限制。

## 規則

- **每個非中途站都可以移動**（末端／轉乘／分歧／交叉點；
  中途站不是頂點）。
- **候選＝八個 1 格單位移動**（`DIRS8`：上下左右＋四個 45° 對角；一次不可超過 1 格——
  要對齊遠處的東西，靠的是 movewise 逐移動壓縮把距離拉近後慢慢完成）。
- **同路線越直越好**（2026-08-08 使用者裁決）：同一條 route 在某站的兩段給「彎折成本」
  ——直穿 180°＝0、一般轉角（直角或鈍角）＝1、**銳角 < 90°＝2**；判準用內積／外積，不用反三角。
  只算**同一條 route**（`sharesRoute`）：不同路線在轉乘站交會成什麼角度不算這條線被折壞。
  - **刻意不區分直角與鈍角**：第一版給鈍角 1、直角 2，等於鼓勵把 90° 換成 135°＋一條 45° 段，
    反而壓低 H/V 占比（台北②實測 H/V 84 → 81、45° 4 → 5）。直角是地鐵圖的正常轉角。
  - **只在「H/V 不變且長度不變」時可以自己證成一個移動**（「純拉直」）；其餘情況只當排序鍵。
    放寬成「可以變長」會與併格互相拉扯、位能不再單調——台北①實測跑滿 200 輪／586 秒
    不收斂，結果還更差（12×11 → 15×12、總長 88.6 → 98.0）。
  - 真正砍銳角的是**收斂後的一次性拉直 pass**（見 system note `route-movewise-loop`）。

- **採納優先序**（四擇一）：
  0. **消交叉**（`occGain > 0`）——與 v 相連的段造成的畫面重疊（壓線＋吞點＋穿越）變少。
     **這一項凌駕其餘所有偏好**，見下方「交叉優先」。
  1. 自身入射段的 **H/V 淨增 > 0**——優先挑淨增最大者。
  2. 若都沒有（`delta <= 0`），但入射段**總長變短**（`shorten > 1e-9`）——挑縮最多者。
- **位移上限**（`DRIFT_CAP`，2026-08-08 使用者裁決）：帶 `anchor` 進來時（循環一定會帶），
  候選位置離錨點的正規化歐氏距離不得超過 `DRIFT_CAP`（現行 `0.20`）；判準＝`driftOk`
  （已超標時只准不變差，見 route-movewise-loop「既有超標豁免」）。
  規格見 system note `route-movewise-loop`。
- **本來已經是直線的，不准變成不是直線**（`STRICT_NO_BEND`，2026-08-06 使用者裁決）。
  這條有**兩個層次，缺一不可**：
  1. **段層**——既有的 H/V 入射段不得變成非 H/V（不看有沒有在別處補回來）。
     取代舊的 `bendsPaid`（原本允許「同一步裡有**同路線**的段被拉直」就折彎既有直段，
     由 `sharesRoute` 判定）。
  2. **頂點層**（`isStraightThrough`／`straightPairsAt`／`stillStraight`）——同一條 route
     原本從某個站**直穿**過去（水平或垂直、兩鄰居分居兩側），不可以在那裡變成轉角。
     **只有段層擋不住**：垂直段變水平段，兩者都算 H/V、段層一定放行，但那個站已經多了
     一個 90° 轉角（2026-08-06 使用者回報的正是這種——分隔站上方垂直、下方由垂直變水平）。
     受影響的頂點只有 v 自己與它的鄰居，所以逐候選檢查很便宜。
  **直穿只認水平／垂直，45° 共線刻意排除**：移除空欄／空列是半平面平移，只有一部分點
  會左移，對角三點必然被打斷——把對角算進來等於每一次壓縮都誤報一次折彎（實測台北
  1264 小步會誤報 141 次）。這也與本系統「直線＝H/V」的既有定義（`countHV`、論文指標）一致。
  舊分支保留在程式裡（`STRICT_NO_BEND = false` 即回到 bendsPaid），預設為嚴格。
  實測：台北 1265 小步、台北＋地標 2310、高雄 163、東京＋地標 3108、紐約 4135、
  紐約＋地標 4620，合計約 15,600 個小步**零次**折彎；同樣的檢查對改動前的程式，
  光台北就抓到 90 次。
- **銳角不可以變多**（`acuteCountOf`，2026-08-08 使用者裁決「點線移動不可以出現路線被
  反折變成 45 度銳角，跟本來的方向反了」）：同一條 route 在某站的兩段夾角 < 90°（判準＝
  兩個方向向量內積 > 0，與 `bendCostAt` 同源）即為銳角，`cross === 0 && dot > 0` 是最極端
  的**完全反折**。移動後銳角對數不得多於移動前。
  在此之前銳角只是彎折成本裡比較貴的一項（2 分）＝**軟的**，所以循環有可能為了多一段
  H/V 而把另一段折回自己身上。三個地方都要擋：移點（本檔）、`rigidShiftCandidates`
  （移線＋移枝）、`hvSpanFreeOnce`（收斂後的優化——多格跳躍最容易折出銳角）。
  與其他軟規則同一層，只有「修交叉」那條路徑豁免（交叉比銳角嚴重）。
  **實測不但沒有代價，整體還更好**：5 城 × 9 鏈，H/V 3888 → **3959**（77.3% → 78.7%）、
  總面積 16066 → **15561**；19 組變好、7 組變差、19 組不變。禁掉銳角等於把貪婪搜尋
  推離那些「賺一段直線、賠一個反折」的死路。
- system note `route-span-cap`：移動後，入射段的兩個非中途站不得橫跨超過上限。
- 每一步都走 makeMover **同一套硬規則**（不新增交叉、不壓到別的線或點、
  象限與邊環繞序不變＝拓撲不變）。
- **tie-break**（排序四層）：H/V 淨增 → 縮短量 → `contScore`（順著同一條 route、
  在鄰居另一側已是 H/V 的段接直——鼓勵延長直線） → 座標決定序
  （col 升序 → row 升序）。

## 交叉優先（2026-08-06 使用者裁決）

> 「出現路線有交叉要想辦法移動到不會交叉的地方」

只要候選能讓 v 的重疊數變少（`M.occlusionAt`），就**略過「直線不可變少」、「不准折彎」
與 SPAN_CAP**——兩條線互相穿過是比「線被折一個彎」或「某段長了一格」嚴重得多的缺陷。
**`validMove` 一項都沒放行**（象限②、邊環繞序④、③不得增加重疊），所以拓撲與相對位置的
保證完全不變。

為什麼三個都要豁免：實測紐約 `algorithm-ortho`，能解交叉的候選**全部**卡在 SPAN_CAP，
不豁免就是死結（解交叉必須把某段拉長一格 → 被否決 → 交叉永遠留著）。

**跑掉的風險有界**：這種移動每次都讓重疊數**嚴格變少**，而重疊數是非負整數且永不增加
（`validMove` 保證），所以整場最多發生「初始重疊數」次；一次一格，跨距最多也只被撐大
那麼多（紐約＝4）。SPAN_CAP 本來就是軟約束、自帶舊長段豁免（system note `route-span-cap`）。

**收斂仍然保證**：位能函數變成 (重疊數, −H/V, 總長) 的字典序——每次採納若不是讓重疊數
嚴格變小，就是在同一個重疊數下讓 (−H/V, 總長) 嚴格下降，兩者都單調有界。

**跨距上限的豁免不在本 pass**（2026-08-08 使用者裁決）：使用者要的「會變成水平垂直就
不看跨距」**只發生在收斂後那一次性的優化步**（`hvSpanFreeOnce`），循環裡的移點一個字
都沒放寬。裁決原文是「前面都還是循環，最後再加一步優化，只執行一次」＋「最後看改了會
變小再改，不用一下子就改」。規格見 system note `route-movewise-loop`「收斂後的優化步」。
**實測佐證這個選擇**：直接放寬循環內的移點條件，45 組裡 21 好但 **6 壞**、總面積 +164；
放到收斂後單跑一次並加上「沒變小就退回」的閘，變成 8 好、**0 壞**、總面積不變。

實測效果（含 ③ 改成「不得增加」一起）：台北＋地標 5 條鏈的網格面積 −3,376 格
（`algorithm-path` 1116 → 352，**−68%**）、大城市 27 組面積 −1,116、跨距超標 −148；
折彎鐵律仍是 0（四城約 10,800 個小步）。紐約的頂點壓線由 1 修成 0；
剩下的 3 對交叉**通不過 ②／④**，那是真正的拓撲限制，只能靠上游別產生。

## 收斂之後為什麼還有斜段（2026-08-06 實測，別再重試一次）

使用者問過「看起來還有很多點可以移動，是不是沒跑完」。**是真的跑完了**——把收斂狀態下
每個頂點 × 八方向重算一遍，紐約 1,264 個候選裡合法的是 **0** 個。剩下的斜段是這套規則
組合的**必然代價**，不是 bug：

| 紐約 `algorithm-ortho` 收斂（38×41、234 段、H/V 165） | |
|---|---|
| 沒有價值的候選（H/V 會變少 997、完全打平 200） | 1,197 |
| 被跨距上限擋 | 39 |
| 被拓撲硬規則擋 | 12 |
| 被「不准折彎」擋（段層 6＋頂點層 10） | 16 |
| **仍可移動** | **0** |

69 條斜段拆開來看：38 條單獨動一端就能拉直（被上表的規則擋住）、16 條要**兩端同時動**、
15 條要移超過一格。

**「兩端協同移動」試過了，是雜訊，已撤回。** 實作方式是單點動不了時，對每條斜段試兩端
的 8×8 組合、拆成兩次單點移動依序過 `makeMover`（拓撲保證不變）。結果：小城市 28 組
面積 +9／H/V +2、大城市 27 組面積 +51／H/V −3／轉彎 +20——沒有一致方向。
原因在收斂點的診斷裡看得很清楚：64 組候選中有 **730** 組「淨 H/V 沒有增加」、
另有 42 組被跨距擋，真正可行的是 **0** 組——那 16 條的每一條都要**犧牲旁邊既有的直線**，
而那正是 `STRICT_NO_BEND` 明文禁止的。**所以這個缺口是被規則關掉的，不是缺功能。**

真要再往前推，只剩兩個槓桿，兩個都與現行裁決衝突，動之前要先改裁決：
① 放寬 SPAN_CAP（最大的單一阻力，39 個候選）——但那正是「相對位置不可以太離譜」那條；
② 允許平手步（那 200 個完全打平的候選）＋tabu——會讓結果對額度參數敏感。

## 收斂

每一步都讓 **(重疊數, −H/V 數, 總長, 同路線彎折成本) 以字典序嚴格下降**——四項都是非負
有界量（長度永不變長：只有「變短」或「純拉直（長度不變）」會被採納），因此必然終止
（movewise 的壓縮會改變長度上界；`MOVEWISE_CAP = 5000` 作為保險）。
