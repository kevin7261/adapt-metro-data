# 非中途站間最大跨距（route-span-cap）

本文件是該演算法／規格的**規格權威**（系統說明，**不是** skill）。實作必須與它相符。

實作：`src/stores/movewise.js` 的 `SPAN_CAP`（模組變數，**預設 4**，來自
`src/lib/layoutDefaults.js` 的 `DEFAULT_SPAN_CAP = 4`——2026-08-06 由 3 改為 4，見下方掃描表）＋ `setSpanCap(n)`
（`Math.max(1, Math.round(+n) || DEFAULT_SPAN_CAP)` — 輸入 NaN 或 0 時 fallback 到預設；否則夾成 ≥1 的整數）；
檢查函式是 `spanOf`／`spanOk`／`boundarySpanOk`。（`hillClimb.js` 再 export `setSpanCap`
供腳本與面板呼叫。）

`resetSpanGapWarning()` 恒為 no-op（S5 結案後保留，避免 `checkSWarnings.mjs` 的舊呼叫點斷裂）。

## 規則

- 任何移動都不得讓**受影響段的兩個非中途站橫跨超過 SPAN_CAP 格**
  （Chebyshev：max(|dx|,|dy|)）——這是為了避免兩點之間的線被拉得太長。
- **舊長段豁免**：本來就超過上限的段只准縮短或維持不變，絕不可再拉長
  （否則它的端點會被永久凍結）。
  實作：`spanOk(A0, B0, A1, B1)` ＝ `ns <= SPAN_CAP || ns <= spanOf(A0, B0)`
  （新跨距 ≤ 上限，或新跨距 ≤ 舊跨距）。

## ⚠ 它是**軟約束**，不是保證（2026-08-06 實測）

這一條**不保證**輸出裡沒有跨距超過上限的段——寫規格或論文時不可以宣稱它是硬上限。
三個原因，都量過：

1. **前期幾乎完全不生效。** 循環的輸入是網格化後的稀疏圖（台北 59×59），
   74 段裡有 49～62 段跨距本來就超過 3——**全部吃豁免條款**，於是規則退化成
   「只准縮短不准拉長」，等於沒有上限。它要到網格壓縮到一定程度才開始真的擋東西。
2. **真正把跨距壓下來的是併格。** 台北從 59×59 壓到約 15×12，跨距是跟著網格一起垮的。
   實證：2026-08-06 給一般合併加上擋格清道（見 system note `route-grid-merge`）之後，
   跨距超標段一口氣少了 298 個——遠多於 SPAN_CAP 本身的貢獻。
3. **輸出仍會超標。** 台北 cap=3 跑完，`algorithm-ortho` 有 5 段跨距超過 3、最大 4 格；
   同一組 cap=999 反而只有 2 段。另外 `shiftAfterClearing`（挪擋格）與併格本身
   都不查 `spanOk`，是規格內明列的旁路。

**那為什麼還留著？** 因為它確實在改變結果——台北 59 個非中途站裡有 39～59 個座標
會因為 cap=3 或 cap=999 而不同。開關之間的品質差異沒有一致方向（H/V ±1～3、
面積互有勝負），所以它的實際角色是**搜尋路徑的擾動參數**，不是品質保證。
2026-08-06 依「有用到就保留」裁決留下，但描述一律照本節，不得寫成硬上限。
- **修交叉時豁免**（2026-08-06 使用者裁決）：移點的候選若能讓畫面重疊（壓線／吞點／
  穿越）變少，就不查這一條——實測紐約能解交叉的候選**全部**卡在跨距上限，不豁免就是
  死結。這種移動每次讓重疊數嚴格變少、重疊數又永不增加，所以整場最多發生「初始重疊數」
  次，跨距最多被撐大那麼多（紐約＝4）。見 system note `route-endpoint-move`「交叉優先」。
- **H/V 變多時豁免——但只在收斂後那一次性的優化步**（2026-08-08 使用者裁決
  「如果會變水平垂直的直線就不看跨距，但如果移了不會變水平垂直才要以跨距為準，
  一樣不能偏離形狀太多」＋「前面都還是循環，最後再加一步優化，只執行一次」）：
  **循環裡的移點／移線／移枝一個字都沒放寬**，跨距上限照舊。唯一豁免的是
  `hvSpanFreeOnce`——收斂後跑一遍、每個頂點最多動一次，候選必須讓該頂點入射段的
  H/V **淨增**才免查 `spanOk`。**位移上限（`DRIFT_CAP`）不在豁免之列**，這是使用者
  那句「一樣不能偏離形狀太多」的落點。規格見 system note `route-movewise-loop`。
  **為什麼不直接放寬循環**：實測直接放寬，45 組裡 21 好但 **6 壞**、總面積 +164
  （紐約 milp／sat 各 −5 段、28×32 → 31×37）——可行域一變，貪婪搜尋的軌跡就跟著變。
  改成收斂後單跑一次、再用「沒變小就整份退回」把關，結果是 8 好、**0 壞**、
  總面積完全不變（H/V 3877 → 3888）。
- **併格會自動滿足上限——但只有合併本身。** 兩兩合併 row／col 是半平面剛體平移，
  只會讓跨距變小，所以不需要檢查。同一步的 `shiftAfterClearing`（挪擋格）仍直接
  呼叫 `M.validMove`，可能拉長跨距——那是擋格清道，不是填空。
  system note `route-grid-merge` 也記了同一條但書。

## S5（已結案 B，2026-08-04）

舊版曾用 `fillEmptyBandsOnce` 把點搬進空列／空欄（緻密化），且不查 SPAN_CAP。
**使用者裁決：空 col／row 只准刪（併格／成對縮），不准填**——該函式已恒 null，
S5 的「緻密化繞過跨距」問題一併消失。刪不掉的空帶可留在 audit（`dense=false`）。

全系統可調參數的總表（在哪、現值、改了要連帶做什麼）＝系統報告
`TUNABLE_PARAMS_REPORT_2026-08-08.md`；本文件是本參數的**規格權威**。

## 設定 UI（StyleBar，**只出現在真正會跑 movewise 的 Straighten 視圖**）

- 「線段最大跨距」輸入框（per-layer 的 `layer.spanCap`，預設 4）。
- **改數字就立刻重算**（@change 直接 emit `recalc-span`）——會清掉三階段／循環／
  逐步／Frame 的快取並用新值重算；D3Tab 用 `appliedSpanCap` 快照「這份快取是用哪個值算的」，
  保證同一個畫面不會新舊上限混雜。
- SPAN_CAP **只約束爬山的 movewise**（移點／移線）；Frame 畫線完全不用它，
  所以 Frame 工具列不顯示這個控制項。
- **llm-skeleton2grid 與 llm-working2grid**（LLM 骨架地圖網格化／LLM 工作地圖網格化）
  雖然是 `type=hillclimb` 圖層，但 UI 歸戶在 GRIDDING、該層本身不跑 movewise，
  所以工具列與資訊說明都不顯示跨距。
- 離線腳本（llmGrid、buildViews 畫廊）使用模組預設值。

## 地標線（河流／公園面域環線）與這條上限

**它不是「所有段都 ≤ n 格」的保證**，這點在地標線上最容易被誤會（2026-08-06 使用者問
「公園 河流 沒有遵守線段最大跨距 n 格嗎？」）。三件事要一起看：

1. **地標線沒有任何特例**——`movewise.js` 整份沒有 `river`／`area` 字樣，地標段與地鐵段
   吃同一個 `spanOk`。
2. **舊長段豁免適用於所有線**：網格化當下就超過上限的段（地標線因為切點少，動輒十幾格）
   只准縮短、不准再拉長，所以它們會一直留著。實測東京＋地標的 ②直角爬山結果：
   地標段平均 5.8 格、最長 18；**地鐵段平均 10.2 格、最長 27**——地標線其實比地鐵線短。
3. **直線化（①〜⑨）不受這條上限約束**：它只擋 movewise 的移動。所以就算在骨架階段
   多切幾個分隔站（見系統說明 `route-skeleton-river`），最終段長仍由直線化決定
   ——實測有城市變短（東京 18→12）、也有城市變長（紐約 16→35）。

**想真的限制最終段長就要動直線化那一層**（把段長放進①〜⑨的成本），不是調這個上限。
反過來說，把上限調小只會讓 movewise 更難移動（很多候選被否決），不會讓既有的長段變短。

## 預設值 3 → 4（2026-08-06 實測掃描）

使用者問「很多明明可以拉直卻沒有，是不是跨距上限的關係？可不可以改成網格長邊的十分之一？」
——**是它沒錯**（紐約收斂點被規則擋下的 67 個候選裡 39 個是跨距上限，最大的單一阻力），
**但十分之一那個規則比現在更差**。掃描四城 36 條鏈：

| 上限 | 台北 H/V／面積 | 台北＋地標 | 東京＋地標 | 紐約 |
|---|---|---|---|---|
| 2 | 575／1491 | 867／3777 | 952／8335 | — |
| **3（舊）** | 586／1421 | 886／3552 | 992／8103 | 1379／14949 |
| **4（新）** | 594／1491 | 903／**3515** | 1009／**6962** | **1424／14562** |
| 5 | 598／1423 | 899／4429 | 1022／7147 | 1427／14761 |
| 6 | 594／1502 | 903／4456 | 1021／7639 | — |
| 8 | 592／1442 | 901／4417 | 1028／7364 | — |
| 不設限 | 588／1606 | 902／4157 | 1051／7357 | — |
| **長邊/10** | **562**／1499 | 889／4242 | 987／7276 | — |

3 → 4 合計：H/V **+87**、網格面積 **−1,495**、總線長 **−571**、轉彎 **−25**；
紐約四項全勝。5 以上 H/V 還會再升一點，但面積開始變差（台北＋地標 3515 → 4429）。

**為什麼「長邊十分之一」不好**：網格會隨併格一路縮小（台北 59×59 → 12×12），
十分之一到收尾只剩 1～2 格，比固定 3 還緊——正好卡死最需要移動的收尾階段，
台北的 H/V 掉到 562（全表最低）。想「早期鬆、後期緊」的直覺與實際需要相反。
實驗碼已移除，別再試一次。

**預設值只寫在 `src/lib/layoutDefaults.js` 的 `DEFAULT_SPAN_CAP`**；
`movewise.setSpanCap` 的 fallback、`bakeStraighteningCells`、`StyleBar` 的兩個輸入框、
`vite/claudeSkillTrigger` 全部改成引用它（2026-08-06 之前這些地方各自硬寫 `3`，
改一半就會出現「網頁用 4、bake 用 3」＝兩張圖不同佈局，直接違反「視圖≡顯示」）。
