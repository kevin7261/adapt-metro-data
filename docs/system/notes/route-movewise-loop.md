# movewise 與程式網絡循環（route-movewise-loop）

本文件是該演算法／規格的**規格權威**（系統說明，**不是** skill）。實作必須與它相符。

定義都在 `src/stores/movewise.js`：`movewiseStage`／`gridMergeStage`／
`straighteningCompactLoop`。`hillClimb.js` 只 re-export 其中七個名字供腳本與面板使用——
`setSpanCap`、`movewiseStage`、`stepChainInit`、`stepChainNext`、`stepChainRemaining`、
`STEP_INFO_START`、`straighteningCompactLoop`——**不含** `gridMergeSweep`／
`gridMergeStage`／`loopPostConverge`。
`movewiseSweep`（走 visited 的單遍掃描版）已**退役**：函式還在，但呼叫點是零；
所有路徑都走 `movewiseStage`。

## movewise

**取消獨立的縮減網格步驟**——移點與移線在**每一個小步驟（單一移動）之後立即**
執行 `compactGridSafe`（實作方式是以 limit=1 反覆呼叫該階段的單掃描 pass、
每個移動後立刻壓縮；`MOVEWISE_CAP = 5000` 作為保險）；併格的半平面平移則
**自帶壓縮**。網格因此隨時保持緻密、尺寸逐步縮小；壓縮只在 movewise 內部使用，
不再是一個 tab。

`MOVEWISE_PASS` 含 `endp`／`line`／`branch` 三個 pass 函式——
`gather` 不在此表，它走 `gridMergeStage` 專用路徑。

**壓縮有硬規則把關**：移除空欄＝右半平面左移 1 格＝ validShift 同一套硬規則
（含變形段檢查，見 system note `route-hillclimb` ③′）——會製造壓點／交叉／共線重疊的空帶
一律**保留**（畫面上多一條空帶），所以佈局永不因壓縮而劣化。

**空列／空欄只准刪、不准填**（S5-B，2026-08-04）：舊版 `fillEmptyBandsOnce` 緻密化
已停用（恒 null）。刪不掉的空帶可留在畫面上（audit `dense=false`），不靠搬點填洞。
`shiftAfterClearing` 仍直接呼叫 `M.validMove`（清擋道），跨距細節見 system note `route-span-cap`。
**2026-08-06 起「刪」的力道變強**：一般合併被少數擋格卡住時會先挪開再併
（`mergeWithClearing`，≤4 個擋格＋H/V 不可變少＋副本試算，見 system note `route-grid-merge`）——
這仍是「刪空帶」不是「填空帶」，S5-B 的裁決不變。實測 55 組網格面積少了約 12,000 格。

## 跑到不動點（movewiseStage）

循環與 system note `route-step-verify` 的「下一步」都是指「該演算法**跑到自己的不動點**」
（`movewiseStage`：同一個元素可以重複移動；併格會一直掃到沒有可合併，
再加上成對縮方）。
**算到不能動才換下一階段／下一輪**——不要只掃一遍就換。

逐步的「下一小步」對移點／移線／移枝而言，取的是與 Stage 相同的「下一個可動」
（**不**使用 visited 集合），這樣小步連跑才不會與最終的循環結果分叉。

## 循環（straighteningCompactLoop）

每一輪＝**移點至不動點 → 移線至不動點 → 移枝至不動點 → 併格至不動點 → 下一輪**；
（移點的採納與排序另含「同路線越直越好」，見 system note `route-endpoint-move`。）
只有當某一輪**四個演算法都沒有任何改動**時才停止（判準與 system note `route-step-verify` 相同；
上限 `LOOP_ROUND_CAP = 200`；矩形凍結時用 `LOOP_ROUND_CAP_FROZEN = 40`，
另外 **stop-thrash**——`rounds >= 6` 且 gather **與 branch** 都已不動、endp 仍反覆同量移動時
計數器 `thrash++`，`thrash >= 3` 即提早停止，避免莫斯科雙環空轉數小時）。
起點會先跑一次 `compactGridSafe`。

收斂之後兩條路徑共用 **`loopPostConverge(skeleton, cur, nC, nR, anchor = null)`**
（**拉直 pass** → 再壓縮＋矩形再試併格／成對縮；**不再填空帶**）。
**`anchor` 一定要傳**——裡面的 `straightenPass` 同樣吃位移上限；逐步驗證那條路徑漏傳過一次，
症狀是與循環的最終座標不一致（見 system note `route-step-verify` 的硬保證最後一條）。

#全系統可調參數的總表（在哪、現值、改了要連帶做什麼）＝系統報告 `TUNABLE_PARAMS_REPORT_2026-08-08.md`；
本文件是本節參數的**規格權威**。

## 位移上限：相對位置不可以跑太遠（2026-08-08）

使用者：「程式網絡循環 點的移動是不是太多造成跟實際相對位置變形太大 這也要調整」。

**先量到的問題**（台北九條鏈，循環結果 vs 網格地圖）：平均位移 10–12%、最大 33–51%，
而且**任兩點的左右／上下順序有 6.7–10.9% 被翻轉**。硬規則②（象限）只保證「相對**鄰居**
不變」，對非相鄰的兩點完全沒有約束——論文 6.1 節本來就寫明正交次序在 movewise 壓縮下是
「有意識地放鬆」。這不是這兩天改出來的（舊版 5.6–10.9%、新版 6.7–8.3%，互有高低）。

**做法**：循環開始時把輸入佈局正規化成 [0,1]² 當**錨點**（`makeAnchor`），之後**移點／移線／
移枝／拉直 pass**的任何候選都不得讓該點離錨點超過 `DRIFT_CAP`（歐氏距離）。
用正規化座標而非格座標，併格與壓縮才不會被誤算成位移——那兩者只是等比縮小整張圖。

### 既有超標豁免：只准不變差（2026-08-08，bug 修正）

`driftOk` 原本是**絕對距離判斷**，沒有豁免——這會把點**永久凍結**：

併格與壓縮**不查位移上限**（它們只縮小網格，本來就免檢），但正規化是除以**當下**的
`cols`／`rows`，所以網格從 35×35 縮到 21×21 時，同一個格座標的正規化位置整個位移。
點因此會在「每一步都合法」的情況下漂到上限之外；一旦漂出去，絕對判準就連
「**往回移、讓偏離變小**」的方向都一起否決，那個點從此再也不能動。

實例＝維也納 45° 的 `n140069854`：偏離 0.296（上限 0.15），八個方向全滅，連移一格都不行
——使用者從 08-08 起反覆追問的「那個點為什麼不動」就是這個，不是跨距、也不是那道閘。

**修法與 `spanOk` 的舊長段豁免同一個模式**：新位置在上限內就過；已經超標時，
只要**新的偏離不大於目前的偏離**（往回走或持平）也放行。呼叫端一律多傳目前位置。
實測 45 組：H/V 3966 → **3973**、總面積 15495 → **15182（−313）**，15 組變好、3 組變差。

**為什麼是上限而不是懲罰項**：懲罰項要進位能函數才不會破壞收斂，而位能已經四層；
上限只是縮小可行域，對收斂論證完全沒有影響。剛體平移（移線／移枝）要求**每個成員**都在上限內。

**上限值＝0.20**。下表是不同上限候選的台北掃描（選定 0.20）：
保留下來是為了看各檔位的走向；調高的實測見表後：

| 上限 | 面積 | H/V | 總長 | 順序翻轉 |
|---|---|---|---|---|
| 0.10 | 1496 | 694 | 931 | 3.8% |
| **0.15** | 1512 | **737** | 918 | **4.8%** |
| 0.20 | 1497 | 736 | 907 | 5.6% |
| 0.30 | 1441 | 721 | 875 | 7.4% |
| 無上限 | **1332** | 692 | **836** | 7.9% |

順序翻轉砍掉 39%，H/V 反而最好；代價是面積 +13%、總長 +10%——正好是使用者優先序的
最後兩名（見 system note `route-grid-straighten-eval`）。

**選定 0.20**。理由：0.15 會讓一些「移過去就能拉直」的
點卡死——維也納 45° 的綠線就是（`n4003977155`／`n140069854` 往左的候選全數被 `driftOk`
擋下，見本檔「既有超標豁免」）。**現行程式碼**（含銳角否決、優化步、既有超標豁免、
形狀沿軸收縮）5 城 × 9 鏈實測：

| 上限 | H/V | H/V 占比 | 總面積 |
|---|---|---|---|
| 0.15 | 3973 | 79.0% | **15182** |
| **0.20（現行）** | **4023** | **80.0%** | 15751（+569）|

29 組變好、6 組變差、10 組不變；順序翻轉由 4.8% 升到 5.6%。**這是「圖更直」與「位置更像
真的」之間的取捨點**，不是一個有唯一正解的最佳化參數——要再動就改這一個常數並同步本節、
`CLAUDE.md` 的不變式②、`route-endpoint-move`、與系統報告 `TUNABLE_PARAMS_REPORT_2026-08-08.md`。

**但這個甜蜜點不普適**：新加坡＋LRT ⑨彈性格網在 0.15 下 H/V 129 → 111（變差）、⑦路徑簡化
119 → 116 但面積 306 → 289（變好）。要調就改 `DRIFT_CAP` 這一個常數（Node 端可用
環境變數 `DRIFT_CAP=` 掃參數），並同步本表。

### 收斂後的一次性「拉直」pass（2026-08-08）

使用者裁決「程式網絡循環要盡量讓同路線越直越好」。循環**裡面**的移點只有在
「H/V 不變且長度不變」時才准為了拉直而動（放寬會與併格互相拉扯、位能不再單調——
台北①實測跑滿 200 輪／586 秒不收斂且結果更差），但那個條件太嚴，實測銳角幾乎砍不動
（新加坡＋LRT 77 → 75）。所以把「**允許變長來換拉直**」獨立成收斂後跑一次的
`straightenPass`：它不在循環裡，就不會跟併格對打。

- **自己會停**：每次採納都讓**全域彎折成本嚴格下降**，而彎折成本是非負整數 → 單調有界。
- **硬規則一條都沒放寬**：`validMove`（不壓點／不新增交叉／象限與邊環繞序不變）、
  `STRICT_NO_BEND`、H/V 不可變少、跨距上限照舊。唯一放寬的是長度可以變長。
- **候選過不了硬規則要換下一個**：第一版直接 `break`，等於第一個候選被擋就整個 pass 收工，
  實測完全沒作用（結果與沒跑一模一樣）。現在依收益排序、逐一試到有一個過。
- **實測（2026-08-08）**：新加坡＋LRT 銳角 ⑨ 77→74、③ 75→74、⑦ 75→73；
  台北④力導向面積 168→132、總長 102.9→92.3。改善幅度有限是**硬規則擋著**——
  收斂後的佈局裡「移一格就能減少銳角且過得了 `validMove`」的頂點只有 22%（⑨）／5%（③），
  其餘是象限／邊環繞序擋住或根本是拓撲逼出來的（LRT 小環在小格網裡本來就轉得急）。——逐步的 done 與執行到底必須走同一套收尾，這樣**最終座標才會與循環一模一樣**。

### 收斂後的一次性「優化」步（2026-08-08 使用者裁決）

> 「如果會變水平垂直的直線就不看跨距，但如果移了不會變水平垂直才要以跨距為準，
> 一樣不能偏離形狀太多」
> 「前面都還是循環，最後再加一步優化，只執行一次」
> 「最後看改了會變小再改，不用一下子就改」

實作接在 `loopPostConverge` 的**最後**（拉直 pass → 壓縮 → 矩形併格 → **本步**），
**移點與移線兩個都要試**（使用者：「移點線在移動限制內的範圍可以讓網格變少就移」）：

1. `hvSpanFreeOnce`——單點直接對齊到能成直線的位置；
2. `lineCompactPass(…, { anchor, hvSpanFree: true })`——整條線的剛體平移，本身就是
   單掃描（每條線最多動一次），`hvSpanFree` 讓 H/V 淨增的平移免查跨距上限。

兩趟接續跑（點 → 線），最後一起過同一道閘。這是全系統**唯一**豁免跨距上限的地方：

- **候選＝直接對齊到能成直線的位置**，不是一格一格挪：對每個鄰居 u 給
  `[u.c, v.r]`（同欄→該段變垂直）與 `[v.c, u.r]`（同列→變水平）兩個目標，可能距離好幾格。
  **逐格版沒有用**——維也納 45° 的 `algorithm-milp` 那個點要往左三格才會與鄰居同欄，
  中間兩步的 H/V 增益都是 0，逐格永遠起不了頭（實測完全不觸發）。
- **只有 H/V 淨增的候選才免查 `spanOk`**；持平或變少一律不走這條路（那些留給循環，照上限）。
- **其餘關卡一個都沒放行**：`driftOk`（＝「不能偏離形狀太多」）、`STRICT_NO_BEND`、
  「不得折彎既有直段」、以及 `makeMover` 的四條硬規則。
- **每個頂點／每條線最多動一次**，單趟掃描，不跑到不動點——這就是「只執行一次」。
- **位移上限（`DRIFT_CAP`）不豁免**（使用者 2026-08-08 明確裁決「不豁免了，還是要看
  位移上限」）：`anchor` 兩趟都照傳。曾試過「只要能讓網格變小就准超出位移上限」，
  45 組實測**0 組觸發**（收斂後單獨移一個點動不了外框，面積不會嚴格變小），已撤除。
- **移線帶來的增益**（45 組實測）：只移點 H/V 3959／面積 15561 → 點＋線 **3966／15495**；
  7 組有變化、**全部變好**（各 +1 段直線，其中 2 組網格縮小），0 組退步。
- **跑完再比一次，兩項都要交代得過去才採用**（使用者：「優化是只有改線和點位置後，
  會讓整個網格再變少、路更直，才改，不然就不用改」）：**網格面積與 H/V 兩項都不可以
  變差，且至少一項要真的變好**（`area1 <= area0 && hv1 >= hv0 && (area1 < area0 || hv1 > hv0)`），
  否則整份退回原狀。
  ⚠ 第一版寫成「面積變小 **或**（面積持平且 H/V 變多）」——那個 or 的第一支單獨成立時，
  可以在網格縮小的同時讓路變不直，正好違反這條裁決。收緊之後 45 組實測**判定完全相同**
  （H/V 3959、面積 15561 一格未變），所以這是零代價的保證性收緊。

**為什麼不直接放寬循環裡的條件**（試過，已撤回）：45 組實測 21 好但 **6 壞**、
總面積 +164（紐約 milp／sat 各 −5 段、28×32 → 31×37）——可行域一變，貪婪搜尋的軌跡
就跟著變。改成收斂後單跑一次＋「變小才收」的閘之後：**8 好、0 壞、37 不變，總面積
完全沒變**（H/V 3877 → 3888），而且循環本身的收斂論證一個字都不用動。

**銳角一律否決**（2026-08-08）：這一步的候選可以跳好幾格，最容易把另一段折回自己身上，
所以與移點／移線同樣受 `acuteCountOf` 把關——移動後同 route 的銳角對數不得變多。
規格見 system note `route-endpoint-move`「銳角不可以變多」。

### 形狀沿自己的軸收縮（`shapeAxisShrinkOnce`，2026-08-08）

使用者：「優化的重點就是要減少網格」。指定形狀城市的外框常常**不是地鐵站撐出來的**，
而是形狀本身撐的——維也納 45° 的多瑙河 7 點共線於 `c+r=23`、兩端在 [3,20] 與 [20,3]、
橫跨 17 格，外框因此必然 21×21、右上一大片空白，移動地鐵站永遠縮不掉。

做法＝把最外側的形狀點**沿著自己的線**一步步往中心拉（保持 `c+r` 或 `c−r` 不變），
每一步都過 `makeMover` 的四條硬規則；收工前驗「所有形狀點仍共線」，不成立整份放棄。
採用條件與本步其餘部分相同：**面積要真的變小、H/V 不可變差**。

**兩個踩過的坑，別再犯**：
1. **整組平移行不通**——`validShift` 八個方向全滅。形狀成員含**與地鐵線共用的交叉點**
   （`expandMembers` 收整條 route 的站），整組搬走等於扯開那些路口。改成「沿線滑動」
   才可行：每個點只在自己的線上動，對地鐵的相對關係變化很小（12 個候選 10 個通過）。
2. **護欄一定要在 `makeMover` 之前設好**——`makeMover` 建構時就把凍結集合抓進去了。
   先建 mover 再清 `members` 完全沒有作用：整個 pass 從不觸發，但每個候選單獨測
   `validMove` 又都是 true。同理**解除範圍絕不可延伸到 `compactGridSafe`**，
   否則壓縮會抽掉對角線中間的空欄、45° 當場被拆散（實測 `c+r` 從單一值變成四個值，
   面積「縮」到 224 其實是圖被壓壞了）。

實測維也納 9 鏈有 7 鏈縮小、45° 全部完好、H/V 不變差：
stroke 441→**304**、milp／octi／sat／flex 441→**306**、path 441→**340**、ortho 440→**342**；
force／lsq 沿軸滑不動維持原樣。一般城市（無形狀護欄）**完全不受影響**（45 組 H/V 一模一樣）。

**它不保證解掉每一個「看起來該拉直卻沒拉」的點**：後面還有位移上限。維也納 45° 的
`n140069854` 就是——跨距那關過了，`driftOk` 仍擋（該點已用完 15% 的位移預算）；
把 `DRIFT_CAP` 放寬到 0.20 它才會走到 `[7,3]`。那是另一條裁決，別在這裡偷改。

診斷用環境變數（都有 `typeof process` 防護，瀏覽器不受影響）：
`DEBUG_OPT=1` 印這一步收了沒、`DEBUG_OPT_NODE=<id>` 印某個點每個候選被哪一關擋下。

**收斂後 dims 安全網**：凍結的矩形頂點偶爾落在宣告網格外一格，
`straighteningCompactLoop` 收尾會撐大 `nC`/`nR` 涵蓋所有 cells——否則下游
`intervalAxes`/`weightedAxes` 的陣列索引會拿到 undefined → NaN → Frame 畫布空白。

**逐步驗證就掛在這個視圖上**：它跑的就是這條循環，所以不再另開一列視圖。
循環視圖＝第一排 StyleBar＋第二排 `D3StepPanel`，且**預設是「最後」**
（＝這裡顯示的收斂結果）；只有按「最前」才會回到第 0 步（＝循環的輸入）。
細節見 system note `route-step-verify`。

## 落檔（「一個 json 只存一個圖」）

鏈資料夾是**容器**，循環結果有**自己的資料夾與自己的檔**：

```
3-straightening/{來源}/[{模型}/]{鏈}/
    {鏈}/                該鏈自己的結果（algorithm-* 是 post；llm-straighten 是 align）
    network-loop/        <- 本規格的產物（程式網絡循環）
    llm-network-loop/    [[llm-network-loop]] 的產物（有跑才有檔）
```

- 檔名從城市 id 起、串接沿途所有資料夾名
  （`as-twn-taipei-3-straightening-grid-algorithm-ortho-network-loop.json`）。
- **移點／移線／移枝／併格不落檔，也沒有自己的視圖列。** 它們在資料流圖上不是獨立節點：
  `src/lib/flowGraph.js` 只用 `role: 'layer'` 建節點，四個階段是以 `sub` 欄位
  **寫在程式網絡循環那個方塊裡面**（`sub: t('d3.loopShort')`，即「移點-移線-移枝-併格」）；
  該處的程式註解明白寫著不另外畫 step pill。`role: 'step'` 確實存在，但在另一張表：
  圖層／代碼對照表 `src/lib/layerRegistry.js` 為 `endpoint`／`linecompact`／`branchshift`／`gridmerge`
  四列標了 `role: 'step'`，供資料流分頁的圖層表使用——**別把兩個檔搞混**。
  UI 上同樣沒有這四個階段的獨立 tab：`D3Tab.vue` 的 `clampStraighteningMode` 會在
  統一格網的 Straighten 圖層上，把 `-end`／`-line`／`-gather`／`-anim`／`-step`
  一律夾回 `-loop`（移枝從來沒有過自己的 mode，不必夾）。四個階段要用時現算（D3Tab 缺了就跑 `movewiseStage`；
  CLI 連算都不算）。改判準時記得 `scripts/bakeStraighteningCells.mjs` 的 `kindDone()`
  只能要求「該有的圖」，多要求一個中間階段＝每條鏈永遠看起來沒做完＝
  沒帶 `--force` 的重跑會把全世界重算一次。
- 路徑一律走 `metroChainCellsPath(cityId, variant, chain, shape, stage)`
  （`stage`＝`post`／`loop`／`llm-loop`），勿手拼字串。
- **資料流圖上①〜⑨合併成一格，磁碟上卻對應 9 個 `network-loop/` 資料夾**——
  這是「節點 ↔ 資料夾 ↔ 檔名 ↔ tag 一對一」不變式的**明示例外**
  （拆成九格會讓圖太高）。除此之外一律維持一對一。
- **循環視圖只有逐步、沒有動畫**（舊的 `st-*-anim` 仍會被 clamp 成 `st-*-loop`）：有逐步
  就不再多一顆播放鍵。
  其餘的 morph 動畫（網格地圖／消融來源／①〜⑨ 結果／LLM 直線化／LLM 指定形狀／LLM 網絡循環）
  一律走 `animMath.morphCellsLayout`（它只把兩端的格座標換成像素，**內插本身是**
  `buildMorphLayout`，與骨架→網格同一支）：中間幀連續內插，格線維持均勻、軸號照順序，
  過程中只有格數多寡在變。
  **LLM 直線化那條的起點不是網格地圖，是直線化結果**（2026-08-11 使用者裁決
  「網格地圖→程式網絡循環是錯的，是 LLM 直線化到程式網絡循環」）——它的循環吃的
  就是那份，所以兩端標籤（`D3Tab.animEndLabels`）與內插起點（`chainStages` 的
  `animStart`、檔案模式則是 `upstreamChainDoc()`）都要跟著改；起點的欄列數要取
  該份佈局自己的外接框，沿用 flow base 的 `cols/rows` 會讓兩端在不同座標系上內插。
- 移點／移線／移枝／併格／程式網絡循環／逐步驗證底下可選的鏈**都不含 hc 鏈**——
  只有九條演算法鏈①〜⑨＋兩條 LLM 鏈（「LLM 直線化」／「LLM 骨架地圖網格化」），
  共 11 條。
- 畫廊縮圖與主視圖同源（都從 cells 現畫）——**任何變更都要更新視圖**，
  見 [[route-view-sync]]。
